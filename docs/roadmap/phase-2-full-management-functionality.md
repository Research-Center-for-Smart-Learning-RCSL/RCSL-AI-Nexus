It was refused by the estimator rather than by the hardware. The six-row measurement is in [PROGRESS.md](../PROGRESS.md) 2026-08-17 and the calibration tables are in `RouteChatRequest`'s module docstring: 1.34x-1.48x high on prose, source and function-tool JSON, and **0.36x on a uuid list**, which is the row that forbids the cheap fix. Dividing the constants by 1.4 to recover the over-count takes the under-count to 0.26, and an under-count is the direction that ends in a prompt the runtime truncates in silence.

  **What is already decided.** The constants are not retuned — the gap runs from 0.36 to 1.48 and no single number sits inside it. The character estimator **stays as the fallback** rather than being deleted: a target with no vocabulary available (MLX, a model registered five minutes ago) must still get an answer from the guardrail, and "no counter, no ceiling" is not an acceptable state for the one check that runs before hardware is committed. And whatever counts must run **before** the concurrency slot is taken, for the reason the slot comment in `RouteChatRequest.execute` gives.

  **What has to be designed, and the hard part is not the counting.** `tokenizers` (the Rust binding) will encode a 300 KB payload in tens of milliseconds, which is a thread-offload question and not a difficult one. The hard part is **binding a vocabulary to the model that will actually serve the request**, because a vocabulary that silently describes a different model is precisely the failure this repository has now recorded twice — the calibration table that described a retired model, and the throughput figure that did. The registry's `ref` is the identity to bind to, and the options are to extract the vocabulary from the GGUF at load time, to vendor a `tokenizer.json` per model family with a checksum the registry pins, or to find a runtime endpoint that will count. **A vendored file with no mechanism tying it to `ref` is not an acceptable answer**; it converts a measurable error into an unmeasurable one.

  **Shape.** A `TokenCounterPort` in `domain/ports`, resolved per target the way `_refuse_what_this_target_would_truncate` resolves the model — which is the line where the target is first known. `_estimated_prompt_tokens` becomes its fallback implementation. `_log_estimate_drift` and `_warn_if_prompt_was_truncated` both stay: the first becomes the instrument that proves the new counter is exact, and the second is the backstop that exists because the runtime truncates rather than refuses, which no counting improvement changes.

  **Done means** the six measured content types all ratio at 1.00 against `prompt_eval_count`, the uuid case no longer under-counts, a payload measured at 99,000 real tokens is admitted by a 122,880 ceiling, the per-request cost on the hot path is measured and recorded rather than assumed, and a model whose vocabulary cannot be resolved still gets the character estimate and a log line saying so.

  **Deployed 2026-08-18 and verified on the machine.** Inside the gateway container the counter agrees with the runtime at +2 on Python source, +2 on a Chinese runbook and +12 on forty tool definitions, with `prepare` at 0.35 s; the model store is mounted read-only and `touch` is refused. The headline case was reproduced end to end: 530,000 characters of prose that the character estimate scores at 176,667 — **1.86x the truth** — and that the old guardrail therefore refused before a model had been chosen, counted at 94,903 against a `prompt_eval_count` of 94,901 and served with `200`.

  **All five hold, measured on the live runtime rather than argued.** Against `/api/generate` with `raw: true` the counts are equal on all six content types, on `qwen2.5:7b` and `qwen3.6:35b-a3b-q8_0` alike; the uuid list the estimator read as 6,660 counts 17,526, which is what the model charges. Through `/api/chat`, which applies the chat template, what remains is a constant — **+2 tokens without tools and +12 with them, the same +12 for 12 definitions and for 60** — so the figure is never below what the runtime charges and never drifts with payload size. Per-request cost is 2.7 ms for 20 KB and 50 ms for 300 KB, on a worker thread; building a vocabulary is 0.14 s to read the header and 0.13 s to build, paid on the load path, and 132 MB resident per vocabulary with two cached.

  **The binding is the weights file, not the runtime's API.** `ref` → manifest → the `application/vnd.ollama.image.model` layer → that GGUF's metadata header, which carries the vocabulary, the merges and the chat template. `/api/show` would have handed over the same arrays; it was refused because the two fail differently, and this repository has twice recorded the failure where the wrong answer looks like an answer. What the format does *not* carry is the pre-tokeniser's regular expression — only the name of a scheme — so that pattern lives in this repository behind an allowlist of the two schemes it has been measured against, and a third scheme falls back to the estimate rather than being split by guess.

  **One thing was decided here that the item did not anticipate.** Exact counting needs the target, the target needs the routing reads, and those reads may not precede the concurrency slot — so the ceiling moved *inside* the slot and what runs before it is a lower bound that no tokeniser could contradict. That is what admits the 140,059-estimated payload: it was refused before any model had been chosen, and the bound now lets it through to a count that says 99,000. The cost is that a payload between the bound and the ceiling waits for a slot in order to be refused, which was weighed against refusing requests the hardware would have served.

- [x] **A place a caller can read their own refusals, and an administrator can read anyone's.** Specified 2026-08-17, done 2026-08-18. **Two people lost an evening each that day to refusals that were correct, permanent, and silent about which of several things they had just changed had caused them.** A `413` said only "The conversation is longer than this platform accepts" — no size, no ceiling, no indication that a new conversation would return the identical refusal — and an operator opened three new conversations against it. A `409` on an API key's expiry said "The model is not in a state that allows this operation", because that error was the platform's general conflict, while the reason sat in `detail`, which does not leave the process; the operator sent it seven times in three minutes and concluded the capability edit beside it had failed. Both messages have since been fixed. **Neither fix helps the next error nobody has thought about**, and nothing on this platform stores a refusal: the gateway logs one and moves on, so answering "what happened at 19:16?" means an administrator reading container logs, which is exactly what happened twice that day.
- [x] **One key may name what serves the model name its client insists on sending.** Done 2026-08-18. `model` taking a capability rather than a model name is this platform's one true divergence, and `capability_not_issued` is the only channel that tells an integrator their client overrode the model line they configured — Codex's picker does exactly that, and three integrations found out through the refusal. **A platform-wide fallback was refused for that reason**: it would buy convenience by making the misconfiguration permanent and invisible. What shipped is opt-in per key, and three properties keep it honest. It is **a substitution, never a widening** — the value must already be in the key's own capabilities, checked at issue, at edit, and once more in `Actor.capability_for`, which re-derives rather than trusts, so a row written by another hand still reaches nothing new. It is **announced**, in `X-Capability-Defaulted`, the same channel and rule as `X-Dropped-Tools`. And it is **recorded**: `usage_records.requested_capability` keeps what the caller actually sent, null when the two agree, because turning the setting on removes the refusal and the evidence has to outlive both a header the client may not read and a log line that rotates. The assistant reads the key's default when it advises on the two key forms, so widening one model does not quietly widen a contract three layers away. Migration `a4c1e07f2b9d`; detail in [backend.md](../architecture/backend.md)

  **The criterion is already established and does not need re-arguing.** `ContextTooLongError` carries `estimated`, `limit` and `composition` on the ground that they describe *the caller's own payload back to them* and disclose nothing the caller did not send; `ApiKeyLifetimeError` carries `maximum_days` on the ground that a published policy is not inventory. `interfaces/http/errors.py` records both. What must not change: the model's alias is still withheld, and `detail` still does not leave the process. A refusal store inherits all three rules.

  **What has to be decided before writing anything.** *Which errors are stored* — every `DomainError`, or the subset a caller can act on. *Retention*, which is a [security.md](../architecture/security.md) §9.2-adjacent question rather than an ordinary one: a refusal is not a transcript, but `composition` describes the shape of a payload and a `413` history describes how somebody works. *Whether the gateway may read the table it writes* — `prompt_logs` says no, and `GATEWAY_DENIED_READ_TABLES` is the mechanism. *Who reads whose* — a key owner seeing their own is the point of the feature; an administrator seeing everyone's is what made tonight's diagnosis possible and needs a scope rather than a role.

  **Shape.** A row written in the same `finally` that records usage, so one write point serves all three entrances, as `prompt_logs` does. A read for the owner under `/me`, a read for an administrator under a scope, and a screen. All 55 `DomainError` subclasses are enumerated in [PROGRESS.md](../PROGRESS.md) 2026-08-17, sorted into the three states they are in: **wrong subject** (fixed that day for the 409 family), **right subject and no figures** — `retention_window_too_long` and `_too_short` name no limit, `invalid_cidr` names no range, `invalid_node_address` names no range, `request_too_large` gives neither size nor ceiling — and **already carrying a caller-facing figure**, which is the nine to copy: `context_too_long`, `capability_not_issued`, `api_key_lifetime`, `insufficient_memory`, `overloaded`, `quota_exceeded`, `rate_limited`, `weak_password` and `upload_rejected`.

  **Done means** an operator who typed an expiry beyond the maximum can find that refusal with its reason without opening a container log, a key owner can find their own `413` with its composition, and nothing in either view names a model or repeats a `detail`.

  **Deployed 2026-08-18, and the deployment found the one defect.** The first real `413` through the deployed gateway was answered correctly and stored nowhere: the API-key resolver never left its actor on the request, and `actor_from_request` is how the exception handler knows who was refused. It had been invisible because the only other consumer of that value is `_audit_refusal`, which returns early on the gateway (§12) — so the one resolver that forgot was the one whose forgetting nothing could observe. Fixed, and pinned by an `ast` rule requiring every public function returning `Actor` in the middleware package to reach `remember_actor`; run against the pre-fix source it names both API-key dependencies. Verified after the fix: the same `413` lands with `basis: tokenizer`, its exact figure, its composition and the caller's request id, and the gateway account answers `permission denied for table refusals` on `SELECT` while `INSERT` succeeds.

  **All three hold, and the first is pinned by an integration test that provokes it.** The expiry refusal lands in `refusals` carrying `maximum_days: 365`, comes back through `GET /admin/refusals` with the request id the caller was handed, and the `detail` naming the date they typed is not in the row. `ContextTooLongError`'s `composition` is stored with the rest of its figures, so a key owner's own `413` carries the breakdown that says which of the three remedies applies.

  **The four decisions the item said to take before writing anything.** *Which errors* — every `DomainError` and the `500` fallback, because a curated subset reproduces the failure this exists for by omitting the error nobody predicted; narrowed only by requiring an identified caller, since an anonymous refusal has no reader and the identity-plane ones are already in `audit_log` by §12. *Retention* — a ceiling of 180 days on a default of 30, with a floor of 7: the ceiling for the §9.2-adjacent reason the item names, the floor because the reader is the person who was refused and a Friday refusal has to survive until Monday. *Whether the gateway may read what it writes* — no, following `prompt_logs`, and `GATEWAY_DENIED_READ_TABLES` is again the mechanism. *Who reads whose* — `refusal:read_own` in the base scopes, because being unable to look up the reason for a refusal is the condition that cost two people an evening, and `refusal:read_all` granted like `usage:read_all` rather than made admin-only beside `prompt_log:read`.

  **One departure from the stated shape, forced by the first of those decisions.** The item asks for a row written in the same `finally` that records usage, so that one write point serves all three entrances. That works for the inference path and only for it: the `409` this feature was measured against was an API key's expiry on the admin surface, which never reaches `RouteChatRequest`. Storing every `DomainError` moves the write to the one place all of them already pass through, the shared exception handler — which also means the figures a row carries are built by the same function that builds the response body, so a stored refusal cannot disagree with the one that was sent.

  **Two of the errors the table above says carry no figures now carry one**, because storing them made the gap concrete: `api_key_lifetime` had `maximum_days` in its sentence and in no field, and `capability_not_issued` had `capability` and `available` the same way. Both are values the caller already holds, and both are now `details` on the response as well as prose. The other four in that table — `retention_window_too_long`/`_too_short`, `invalid_cidr`, `invalid_node_address`, `request_too_large` — are unchanged and still owed one.

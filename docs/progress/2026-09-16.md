## `ExitTimeOut` 設上去了，三段會跟 `KeepAlive` 打架的程序也修了

2026-09-10 辨識出的資料損失風險：`online.rcsl.colima.plist` 沒有 `ExitTimeOut`，
吃 launchd 的 20 秒預設。`colima stop` 的序列（卸載磁碟、停 VZ、停 hostagent）
經常超過 20 秒，而 `bootout` 和 macOS 關機都是 SIGTERM 加 `ExitTimeOut` 後的
SIGKILL。那個磁碟映像裝著全部的 named volume——Postgres 與 Redis 的全部狀態。

plist 加了 `ExitTimeOut=120`，給 `colima stop` 的序列充裕的時間。

同一天辨識出的第二個問題：`KeepAlive=true` 在 2026-09-09 修好 spawn 之後開始
生效，但 repo 裡三段寫著 `colima stop` 的程序都是在 launchd 不管事的前提下寫的。
照著做的人會在 `colima stop` 之後十秒內被 launchd 拉回來，而 colima 在 start 時會
改寫 `colima.yaml`。三處都改成 `bootout`/`bootstrap`：

- `09-build-deploy-and-upgrade.md` 的 `mounts:` 修改步驟
- 同檔的 `[Updated 2026-09-05]` 段落
- `first-deploy.md` 的疑難排解手動補救

`planned-shutdown.md` 的兩個修正：

- 第 3 節「回頭確認」：拿掉「這一步預期會是空的」。那句話的證據來自 bootstrap
  （啟動），不是 bootout（停止）。對一個 launchd 真的持有的 colima 做 `bootout`
  到今天為止仍然沒有執行過。改寫成明確標記未驗證，並說明 `ExitTimeOut` 已設但
  仍需演練確認。

## 把 read timeout 提到超過 prompt evaluation 的實測耗時

2026-09-02 量到的問題：`MAX_CONTEXT_LENGTH=122880` 在 gemma4 的 88.4 tok/s 下要 1379
秒，但 `REQUEST_TIMEOUT_SECONDS=1200`。guardrail 放進來的請求，transport 會砍掉。

這是三個值要一起動的關係：context ceiling、read timeout、`proxyTimeout`。四個選項裡
選了**提高 timeout**而不是降低 ceiling，因為 ceiling 是三次為了 agent client 加上去的，
而 timeout 的代價只在 runtime 完全掛掉時才出現——hung runtime 佔一個 slot 25 分鐘
而不是 20 分鐘，4 個 slot。

| 值 | 舊 | 新 | 為什麼 |
|---|---:|---:|---|
| `REQUEST_TIMEOUT_SECONDS` | 1200 | 1500 | 1379s 的實測值 + 8.7% headroom |
| `proxyTimeout` | 2,160,000 ms | 2,460,000 ms | 必須 > 1500 + 900 = 2400s |
| `MAX_CONTEXT_LENGTH` | 122,880 | 不動 | 降它等於拿回 agent client 需要的空間 |

`test_proxy_and_body_limits.py` 通過——它讀兩個檔案、驗證 `proxyTimeout` 嚴格大於
`REQUEST_TIMEOUT_SECONDS + GENERATION_DEADLINE_SECONDS`，這個跨語言的 invariant 是
2026-08-14 那次 timeout 提高忘了同步時被抓到才加的。

`decisions.md` 的對應 item 標記為已解決。`max_context_length` 和
`request_timeout_seconds` 的 docstring 都更新了，包括 `generation_deadline_seconds`
裡引用的已經不對的 556 秒。

## 修好 spawn 的那個 commit，也讓 `KeepAlive` 第一次真的生效

`c890aa4` 把 `colima` 與 `socat-forwards` 的 `StandardOutPath` 移到
`/opt/homebrew/var/log`，並給 colima 一條看得到 `limactl` 的 `PATH`。那兩個
defect 都修對了，前一天的紀錄也把原因追到底了。但一次程式碼審查在這個 commit 上
問了一個它自己沒問的問題：**這兩個 job 從來沒有被 spawn 過，那 plist 裡其他一直
寫在那裡、卻從來沒有機會執行的欄位，現在會怎麼樣？**

答案是 `KeepAlive` 和 `ExitTimeOut`。兩者都不是這個 commit 寫的，兩者都是因為
這個 commit 才開始有作用。

`online.rcsl.colima.plist` 的 `KeepAlive=true` 在 2026-09-09 之前是一段死碼——
launchd 既然沒 spawn 過這個 job，也就無從「保持它活著」。現在它活著了。而 repo 裡
每一段寫著 `colima stop` 的程序，都是在 launchd 不管事的前提下寫的：

- [`architecture/deployment/09-build-deploy-and-upgrade.md`](../architecture/deployment/09-build-deploy-and-upgrade.md) 第 84 行（改 `mounts:` 之後重啟 VM）
- 同檔第 204 行（`colima stop && colima start`）
- [`runbooks/first-deploy.md`](../runbooks/first-deploy.md) 第 1072 行

照著做的人會在 `colima stop` 之後的十秒節流內，被 launchd 用
`colima start --foreground --memory 3` 搶先拉起來——而 colima 在 start 時會**改寫**
`~/.colima/default/colima.yaml`，也就是他剛剛編輯的那個檔案。接著他自己那行
`colima start` 再撞上去。這三段程序現在都需要先 `bootout`，或者整段改成
`bootout`／`bootstrap` 一對。

## 第二件事比較嚴重，而且它動到的是資料

`online.rcsl.colima.plist` 沒有 `ExitTimeOut`，所以吃 launchd 的 20 秒預設。

在 launchd 真的持有 `colima start --foreground` 之後，
[`runbooks/planned-shutdown.md`](../runbooks/planned-shutdown.md) 第 201 行的
`launchctl bootout system/online.rcsl.colima`、以及 macOS 自己的關機，都會送
SIGTERM，然後在 20 秒後送 SIGKILL。而同一份 runbook 下一節就寫著 `colima stop`
要做的事是「卸載磁碟、停 VZ、停 hostagent」，那個序列經常超過 20 秒。

中途被 SIGKILL，等於在磁碟映像還沒 flush 的情況下砍掉 VM。那個映像裝著全部的
named volume，也就是 Postgres 與 Redis 的**全部狀態**
（見 `09-build-deploy-and-upgrade.md` 第 85 行）。

**這個曝險是 `c890aa4` 新產生的**，不是本來就在那裡的：在那之前 launchd 從來沒有
對這些程序送過任何訊號。`ExitTimeOut` 應該設到一個舒服地高於實際 `colima stop`
耗時的值。

## 一句沒有證據支撐的話，要先拿掉

`planned-shutdown.md` 第 210 行寫著「`bootout` 對六個都成立，這一步預期會是空的」。

支撐它的是 2026-09-09 的驗證，而那次驗證的內容是 `active count = 1` 與 foreground
的日誌行——**那證明的是 `bootstrap` 現在會動，不是 `bootout` 會乾淨地停。**
2026-09-09 是一次復機，不是一次停機；對一個真的由 launchd 持有的 colima 做 `bootout`
到今天為止一次都沒有執行過。

而把上一節接上來，`bootout` 最可能的實際結果是 SIGTERM 加 20 秒後的 SIGKILL，不是
同一節堅持要有的那個乾淨的 `colima stop` 序列。把後續那一步降級成「預期是空的」，
等於邀請下一個 operator 跳過它，而根據的是一句沒被測過的話。

這跟前一天那個教訓是同一件事的第二次出現：**那是機制，不是原因**——這次是
**那是 bootstrap 的證據，不是 bootout 的證據**。

## 順帶一個會讓人卡住的迴圈

`planned-shutdown.md` 第 313 行的 `until docker info >/dev/null 2>&1; do sleep 2; done`
沒有上限，等待期間也不印任何東西。2026-09-09 加的那條註記修好了它的身分問題
（要用 `sudo -u … -H`，socket 在 `~/.colima/default/docker.sock`），但迴圈本身還是
沒有 deadline、也沒有指向日誌。

而 `c890aa4` 修的正是「colima 在 launchd 下永遠起不來、每十秒重試一次」那個狀態。
在那個狀態裡，這個迴圈會讓 operator 無限期地掛著，畫面上什麼都沒有。應該給它一個
期限，逾時就指向 `/opt/homebrew/var/log/nexus-colima.log`，以及同一節已經寫好的
`active count` ／ `state =` 檢查。

## 哪些是驗過的，哪些不是

這一份要分清楚，否則它會變成它自己在批評的那種東西。

**對照過實機驗證的**：`/opt/homebrew/var/log` 是 `rcslmac1:admin drwxr-xr-x`，
其餘 nexus daemon 都已經寫在那裡，所以「只有這兩個是那個組合」成立；九個 plist 的
`plutil -lint` 全過；repo 裡那兩個 plist 與 `/Library/LaunchDaemons` 的安裝版
逐位元組相同；`/var/log/nexus-*` 的舊路徑除了歷史紀錄以外沒有殘留；socat 那支腳本
確實用絕對路徑呼叫 `socat` 與 `ifconfig`，所以不給它 `PATH` 是對的；runbook 對
docker context 的說法與實機 `docker context ls` 相符；`nexus-colima.log` 顯示這個
job 現在確實跑到 `keeping Colima in the foreground` 且 `$HOME` 正確。

**沒有驗過的，全部是後果推論**：`KeepAlive` 與 `colima stop` 的競爭、20 秒
SIGKILL 對磁碟映像的影響、`bootout` 對一個 launchd 持有的 colima 究竟會發生什麼。
第三項尤其是重點——**它從來沒有被執行過，這正是上一節要拿掉那句話的理由，
所以這一份也不能反過來斷言它會壞。**

要把這三項從推論變成事實，需要的是一次刻意的停機演練，而不是等下一次真的要關機時
才知道。演練順序應該是：先設 `ExitTimeOut`、再做一次 `bootout` 並計時、
確認 VM 是走完 `colima stop` 序列還是被砍掉。

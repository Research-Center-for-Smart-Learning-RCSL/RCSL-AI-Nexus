## 復機時發現：那兩個 daemon 從來沒有被 launchd 起過

前一天的停機留下一個沒答完的問題。`bootout` 對六個 daemon 裡的四個有效，對
`colima` 和 `socat-forwards` 無效，而當時寫下的原因是「這兩個 job 的工作程序已經
reparent 到 PID 1」。那是機制，不是原因——它沒有回答「為什麼偏偏是這兩個」。

今天第一次真的走完復機程序，同樣是這兩個起不來，才把原因逼出來，而它比前一天的
說法更根本：**launchd 從來沒有 spawn 過這兩個 job。**

`launchd` 是以 job 的 `UserName` 身分去開 `StandardOutPath`，不是以 root。這兩個
plist 的日誌寫在 `/var/log`（`root:wheel drwxr-xr-x`）而 `UserName` 是 `rcslmac1`，
建檔拿到 `EACCES`，spawn 在程式執行之前就失敗。六個 daemon 只有這兩個是這個組合，
其餘都寫在 `/opt/homebrew/var/log`——而它們正好就是 `bootout` 停不掉的那兩個。這不是
巧合，是同一件事的兩面：**停不掉，是因為那些程序從來就不是 launchd 的子程序。**
它們是某次手動 `colima start`、手動跑那支 socat 腳本留下來的，脫離終端機後
reparent 到 PID 1，然後一直活著。

證據是三項，缺一項都還能狡辯過去：`/var/log/nexus-colima.log` 與
`/var/log/nexus-socat-forwards.log` **從來不存在**（不是被輪替掉的，newsyslog 沒有
nexus 的規則）；`launchctl print` 顯示 `active count = 0` 配 `state = spawn
scheduled`；以 `rcslmac1` 在 `/var/log` `touch` 直接得到 Permission denied。

**這個失敗從外面完全看不見，這是它能潛伏數週的原因。** `bootstrap` 依然回傳 0，因為
「把 job 載入 domain」確實成功了，失敗的只是 spawn。前一天的 runbook 寫下「不要看
`bootout` 的回傳值，要看程序」，方向對了；今天補上的是另一半：**`bootstrap` 的回傳值
同樣不是程序起來了的證據**，而診斷它的欄位是 `active count`，不是結束碼。

兩個缺陷同時在 `106c412`（Replace Docker Desktop with Colima）進來——同一個 commit
加了 `UserName`，也加了 `/var/log` 的路徑。單獨看任何一個都沒有問題，是這個組合有
問題，而 code review 讀的是 diff、不是 `/var/log` 的權限位元。

修法是把兩個 plist 的 `StandardOutPath`／`StandardErrorPath` 移到
`/opt/homebrew/var/log/`，與其餘六個 daemon 一致，並在 plist 裡把理由寫在旁邊——這種
「移一個路徑」的改動，沒有註解就會在下一次整理時被移回去。

## 修好第一個缺陷，第二個才現形：兩個缺陷互相遮蔽

日誌路徑修好、job 終於 spawn 起來之後，它做的第一件事是每 10 秒吐一行：

```
lima compatibility error: exec: "limactl": executable file not found in $PATH
```

launchd 給 job 的是最小 PATH（`/usr/bin:/bin:/usr/sbin:/sbin`），而 `colima` 只是一個
wrapper，真正做事的 `limactl` 在 `/opt/homebrew/bin`。`KeepAlive=true` 把它變成一個
十秒一次的無限失敗迴圈——這也是這次唯一一段平台真的離線的時間，因為交還 VM 給 launchd
的那一刻，手動起的那個實例就沒了。

**這兩個缺陷的關係比「同一個 plist 有兩個 bug」更有意思：它們互相遮蔽。** 日誌不可寫，
spawn 在程式執行前就失敗，所以 PATH 的錯誤永遠印不出來；而在終端機手動 `colima start`
一定會成功，因為操作者的 shell 有 Homebrew 在 PATH 上。**兩個缺陷都只在 launchd 底下
發作，而且必須先修好第一個，第二個才看得見。** 這解釋了為什麼「先手動起 colima 讓服務
先回來」這個看似務實的中途決定，其實也是在延後發現——手動路徑正是繞過這兩個缺陷的
那條路。

順帶一提，這也是為什麼修完要看的是日誌最後一行寫著
`keeping Colima in the foreground`、`launchctl print` 的 `active count = 1`，而不是
`bootstrap` 的結束碼。三次 bootstrap 全部回傳 0，三次的實際結果分別是：沒 spawn、
spawn 後無限失敗、正常運作。

## 復機路上的第二個坑：等 docker 就緒的檢查要用誰的身分跑

第一支復機腳本在「等 docker 就緒」那一步白等了 180 秒然後放棄，而當時 colima 確實
沒起來（那是上面那個 bug），所以這個缺陷差一點就被隱藏過去。

`colima start` 會建立並切換到 `colima` 這個 docker context，endpoint 是
`~/.colima/default/docker.sock`，而 context 的選擇存在 `$HOME/.docker`。腳本在 root
的 shell 裡用 `sudo -u rcslmac1 docker info` 檢查——**沒有 `-H`**，所以 `$HOME` 還是
`/var/root`，docker 落回 `default` context 的 `/var/run/docker.sock`，而那個 symlink
指向 Docker Desktop 時代的 `~/.docker/run/docker.sock`，早就不存在了。

也就是說：**就算 VM 正常起來，這個檢查也永遠不會過。** 它是一個會把成功誤判成失敗的
就緒檢查，而就緒檢查誤判的方向決定了它是煩人還是危險——這個方向是安全的（不會在 VM
沒好的時候往下跑 compose），但它會把一次正常的復機變成一次除錯。已寫進 runbook 第 6
節。

## 順帶記下一個容易誤讀的訊號

復機途中一度判定 `health-check` 在停機時被 bootout 了，理由是 `nexus-health.log`
停在 23:35 之後就沒有新行，而且 `pgrep` 也找不到程序。兩個訊號都不成立：那支腳本
**只在簽章*改變*時寫日誌**，23:35 之後平台的失效簽章就穩定了，所以沒有新行是正確
行為；而它是 `StartInterval=300` 的週期性 job，兩次執行之間本來就沒有常駐程序可以被
`pgrep` 找到。它整段停機期間都活著——今天 00:05 平台狀態一變，它立刻寫了新行並寄了
信，那封信就是證據。（前一天的紀錄沒有做過這個推測，這是復機當下的誤判。）

日誌的沉默不等於程序的沉默，這跟同一份 runbook 裡「`observed_at` 要表示*最後觀測*而
不是*最後改變*」是同一個教訓的兩次出現。

## 寫入在回應送出前 commit（#45、#46）

FastAPI 0.139 預設 scope 的 `yield` dependency，要等回應送出**之後**才結束；而 `get_session` 是在結束時 commit。所以每個管理寫入都是先回 200、後 commit，造成兩個問題：

- 客戶端拿到 200 後立刻讀回，可能讀到舊資料。`routing-selection` e2e 從 8/18 起的間歇失敗就是這個原因。f9e3a97 加的證據收集在 10/09 給出答案：瀏覽器放棄時，後端和代理都已經是新值。
- commit 如果失敗，客戶端仍拿到成功，寫入卻遺失了。

**修法。** `SessionDep` 改成 function scope 的 `_commit_before_response`，它包在原本 request scope 的 `get_session` 上，拿到的是同一個 session：

- handler 返回時就 commit，所以 commit 失敗會變成這個請求的 500。
- 串流在 handler 返回後繼續用同一個 session 寫 usage，這部分照舊由 `get_session` 在最後 commit。

沒有採用「兩個 session dependency」的做法：FastAPI 的 dependency 快取 key 包含 scope，同一個請求兩邊都用到時會拿到兩個 session。

**測試與驗證。**

- `test_commit_before_response.py` 在回應狀態列送出的那一刻，用另一條連線查資料：修正前是 0 筆，修正後是 1 筆。
- 部署後在 gateway 容器內實測：plain 和串流的 chat 都是 200，usage 各寫入一筆。

## 部署時 colima VM 記憶體不足

前一天收尾時清了 Docker 建置快取，這次建置因此要從頭編 Rust 和前端。colima VM 只有 3 GiB、沒有 swap，正式服務又在跑，結果 08:16–08:17 發生 `global_oom`，被殺掉的有：

- 10 個 uvicorn worker；
- 3 個 next-server；
- grafana。

第一次建置也因此被取消，第二次才成功。那一分多鐘內，正式服務的請求可能失敗。

現在快取已經重建，之後的建置會回到增量編譯。教訓是：在這台主機上，正式服務運作時不要清建置快取，不然下一次完整建置就會和正式服務搶記憶體。**VM 加到 4 GiB（維護者決定，08:43）。** 為了估算需要多少，在主機上實測了兩個建置的峰值：

- `next build` 1.96 GiB；
- Rust 編譯（4 個 job）1.27 GiB。

加上平常運作的約 1.8 GiB，以及 BuildKit 的約 0.5 GiB，從頭建置需要：

- 兩個建置同時跑：約 5.5 GiB；
- 依序跑：約 4.3 GiB。

所以 4 GiB 能涵蓋平常的增量建置，但仍不足以在正式服務運作時從頭建置。調整過程：

1. `colima stop` 後，以 `colima start --memory 4` 重新啟動，停機約 17 秒。
2. 12 個服務自動回來，Postgres 乾淨關機後重啟，健康檢查通過。
3. chat 經 agent 正常，plain 與串流的 usage 都有寫入。
4. 主機上 Ollama 的模型（合計 39.1 GiB）不受影響。

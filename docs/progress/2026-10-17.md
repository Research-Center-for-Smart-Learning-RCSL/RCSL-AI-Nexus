# 2026-10-17

## Platform restored; `qwen7b` no longer resident

The platform had been stopped with no models resident while PRs #56–#66 were
reviewed and merged. It was brought back today. The work below was done
without sudo, which leaves two gaps; they are listed at the end.

**Order.**

1. Started the Colima VM by hand with `colima start --memory 4`, as on
   2026-10-10. The old containers came back with it.
2. Ran a backup. Nightly backups had failed since 2026-10-11 because Postgres
   was down; this one completed with no repository errors.
3. Built `main` at `27a86f7`.
4. Stopped `gateway`, `admin-public` and `admin-tailnet` before migrating, as
   [2026-10-14](./2026-10-14.md) requires for per-attempt settlement.
5. Ran `migrate`, which applied five revisions to `a4d81c6e9f27`.
6. Started the new containers in this order:
   1. `node-agent`;
   2. `admin-tailnet`;
   3. `gateway` and `admin-public`;
   4. the rest.

All services became healthy. The agent took the node without refusal: no
operation was `running` or `outcome_unknown`. Models were loaded directly
through Ollama with `keep_alive: -1` and the registered context lengths.

**The three-model set does not fit at 4 GiB.**

- `gemma4:31b-it-q8_0` loaded at `num_ctx` 262144. Ollama then reported
  `system_free` 6.0 GiB.
- `qwen2.5:7b` at 32768 was predicted at 6.1 GiB, so loading it evicted gemma4.
- A second attempt loaded gemma4 alone and sampled free pages every 5 seconds
  for 90 seconds. They stayed at 0.1–0.3 GiB and did not recover.

The difference from the 3 GiB measurement is the VM.

- The VM's host footprint was 4.1 GiB with the containers using under 1 GiB
  inside the guest.
- Dropping the guest page cache (`drop_caches`) freed memory inside the guest
  but did not change the host footprint. Virtualization.framework does not
  return it, so the cap, not the guest's use, is what the host loses.
- At 3 GiB the margin was already only 1–3 GiB ([2026-09-07](./2026-09-07.md)).
  The extra 1 GiB removes it.
- No other process on the host used significant memory.

**Decision (maintainer): `qwen7b` is not kept resident.**

- `gemma4-31b-q8` and `embedder` are resident.
- `chat` already falls back to gemma4 when qwen7b is not resident.
- `assist` named qwen7b alone. That would have refused the management
  assistant and Tier 2 compaction, which routes on `assist` and has no
  fallback. gemma4-31b-q8 was added to `assist` at priority 200 behind
  qwen7b at 100.
- The change went through `ManageRoutingPolicies.save` in the admin container
  as the maintainer's administrator account, so it carries the normal
  validation and a `routing_policy.saved` audit row.
- The live routing service resolves `assist`, `chat` and `code` to
  gemma4-31b-q8 and `embedding` to embedder.

The other two options were rejected:

- Returning the VM to 3 GiB brings back the rebuild OOM of 2026-10-10.
- Halving gemma4's context costs the longest-context work.

qwen7b keeps `desired_resident = false`. Its legacy `state` column still
reads `loaded`. Routing and the budget read observation first, so this has no
effect. Correcting it would need a Load and Unload, and the Load would evict
gemma4.

**Left open (needs sudo):**

- **The installed `online.rcsl.colima.plist` still carries `--memory 3`, and
  the VM now runs outside launchd.** The job's original foreground process
  from 2026-10-07 is still alive. A host reboot would start the VM at 3 GiB.
  The other three drifted plists (`backup`, `health-check` and
  `reconcile-port-bindings`) differ only in comments.
- **Host acceptance for #49 and #23 was not run.** It needs an Ollama restart
  through `launchctl kickstart`.

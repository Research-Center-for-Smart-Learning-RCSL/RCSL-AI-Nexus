## The deployment had moved away from the documents, and the harness written to protect it had gone stale in exactly the way its own comment predicted

**What is serving is `gemma4-31b-q8`, and every document says otherwise.** The
`routing_policies` table reads `code` → `gemma4-31b-q8` and `chat` → `qwen7b`
(100) then `gemma4-31b-q8` (200); `/api/ps` agrees; `qwen36-35b-a3b-q8` is
`downloaded` and not resident. The audit log dates it exactly: at 07:58:13 on
2026-08-21 `routing_policy.saved` put `code` back on `gemma4-31b-q8`, and at
07:59:36 `chat` followed. The whole move took two and a half minutes —
`qwen36-35b-a3b-q8` unloaded at 07:57:20, `gemma4-31b` (the q4 QAT) loaded at
07:57:39 and unloaded again 45 seconds later, `gemma4-31b-q8` loaded at
07:58:39, `embedder` and `qwen7b` behind it.

**Why is not knowable from here, and this entry does not guess.** The audit log
records what was done and by whom, never a reason; [2026-08-21](./2026-08-21.md)
records a frontend pass and two deploys and does not mention the model at all.
What can be said is that the switch the 2026-08-15 evaluation argued for — 4.6
points of capability for a round in 45% of the wall clock — was reversed six
days later and left unrecorded, so
[decisions.md](../roadmap/decisions.md)'s account of it has been describing a
deployment that does not exist for twelve days.

**One detail of the sequence is worth keeping.** Between 07:58:13 and 07:58:39
the `code` policy pointed at `gemma4-31b-q8` while the model actually resident
was `gemma4-31b`, the q4. Every candidate in that policy requires
`model_state: ["loaded"]`, so for twenty-six seconds `code` had no viable
candidate. Nothing was serving at the time and nobody saw it. It is recorded
because it shows the order was improvised rather than followed.

**`scripts/model-eval/run.py restore` would have made this worse, and its own
comment says so.** The `DEPLOYED` literal named `qwen3.6:35b-a3b-q8_0` alone,
correct when it was written on 2026-08-15 and wrong from 2026-08-21, above a
comment reading *"Whoever runs this next has to check the line still describes
the deployment before trusting it; nothing here can detect that it has gone
stale."* Run today it would have evicted what is serving and loaded what is
not. Two further defects were in the same function and neither was about
staleness: it restores one model where the deployment holds three, so `assist`
and `embedding` stayed down after every restore; and it warms every model
through `/api/generate`, which an embedding model answers `400 does not support
generate` — the platform's own adapter has handled that since it was written,
and the harness never did.

**The fix is to stop asking a literal to be right.** `run()` now calls
`snapshot()` before the first eviction, writing residency and each model's
context length to `deployment-snapshot.json`; `restore()` prefers that file,
falls back to the literal with a loud warning, warms through `/api/embed` when
generate is refused, and removes the snapshot once it has succeeded. The
snapshot is written once per run and survives an interrupted phase, because the
resume case is precisely where a second snapshot would capture the harness's own
model and call it the deployment. `DEPLOYED` is corrected to today's three
models and is now a fallback rather than the source. The staleness class is
gone rather than the instance.

### How far one unrecorded change reached

**Eleven places named the wrong model or reasoned from its numbers**, and they
were found by grepping for the alias rather than by anything noticing. Four
were prose an operator or integrator would act on —
[connect-an-agent-client.md](../runbooks/connect-an-agent-client.md) told a
Codex user which model `code` reaches and quoted a latency measured on it,
[phase-2](../roadmap/phase-2-full-management-functionality.md) read as though
the 2026-08-16 switch were still in force, `.env.example` derived the context
ceiling from that model's throughput and pinned its truncation point, and
[first-deploy.md](../runbooks/first-deploy.md) §5.1 presented exact token
counting as something a correct mount buys.

Three were worse than prose. **[security.md](../architecture/security/13-phased-rollout.md)
§13.0 is the control-by-control inventory of what exists**, and its row for
exact prompt token counting claimed a control that has not covered `chat` or
`code` since 2026-08-21 — the mechanism works, its coverage does not, and a row
that does not separate those two is the kind of entry this repository has
already recorded eight of. §4's data-plane table said the read-timeout margin
*"has widened rather than narrowed"*; it is negative.
[deployment.md](../architecture/deployment/10-configuration-and-secrets.md) §10
said the read timeout "is no longer the binding constraint".

Four were docstrings, which is where an engineer looks when the documents
disagree. `runtime.py` carries the authoritative account of
`max_context_length` and `request_timeout_seconds` and stated the coupling as
comfortable; `estimates.py` listed the paths on which the estimator is still
used as three edge cases — an MLX target, a model registered but not pulled, a
host without the store mounted — and the fourth, unlisted because it had not
happened yet, is now the main road. `estimates.py` also gained something better
than a correction: the first of its two calibration tables was measured on
`gemma4-31b`, which carries the same 262,144-entry vocabulary as the model
serving today, so **the table that was superseded on 2026-08-17 came back into
force on 2026-08-21** and nobody had to measure anything to know it.

**None of this was caused by the revert being wrong.** It may well have been
right; nothing here establishes either way, because no one wrote down why. What
it cost was eleven documents, two of which are the ones this repository points
at when it wants to know what is true.

## Upgrading the runtime, and the two gigabytes it quietly took

**Qwen 3.8 27B needs Ollama 0.32.12 and this host was on 0.32.4.** Support
landed on 2026-08-14 (0.32.12), developer instructions the same day in 0.32.13;
the installed build predated both by two and a half weeks, so the model could
have been pulled and could not have been run. Homebrew offered 0.33.2.
Procedure, the checks after it, and the failure mode in the middle are now in
[deployment.md](../architecture/deployment/09-build-deploy-and-upgrade.md) §9,
which had nothing about the runtime at all — §9 is titled *Build, Deploy, and
Upgrade* and covered only containers.

**The upgrade leaves a window where the runtime answers and cannot load.**
Homebrew's automatic cleanup deleted the 0.32.4 Cellar as part of the upgrade,
and the running server loads its inference workers from
`Cellar/<version>/libexec/lib/ollama/llama-server` inside it. The three workers
already running held open inodes and kept serving — `/api/version` still said
`0.32.4`, `/api/ps` still listed three resident models — while any *new* load
had nowhere to load from. A health check that asks whether the runtime answers
cannot see this. The two commands belong together.

**It is also the one upgrade on this host with no local rollback**, for the same
reason: §9's rollback is a git checkout and a rebuild, and here the previous
binary is deleted from the machine by the upgrade itself. Going back means
recovering an old formula from `homebrew-core`'s history. That was not known
before it happened and is now written down.

**The restart costs a memory budget line, and it is not small.** At the same
262144 context and the same quantisation, `gemma4:31b-it-q8_0` is **33.55 GiB**
resident under 0.33.2 against 31.58 under 0.32.4. Summed over the three
resident models the budget's `in_use` moves from 37.25 to 39.21 GiB, so the
headroom under the static `64 × 0.8 = 51.2` falls from **13.95 to 11.99 GiB** —
1.97 GiB, for nothing anyone asked for. The heartbeat wrote the new figure into
`observed_memory_gb` within its thirty-second interval with no intervention, and
`MemoryBudgetService` used it immediately, so the guardrail behaved correctly;
what changed is how much room is left for a model that is not yet loaded. That
is the number any decision to add a fourth model has to be taken against, and it
moved without a decision.

**Everything else was checked rather than assumed.** 0.33.2 running as
`_rcslollama`; the runtime answering on `127.0.0.1:11434` and refusing on both
`192.168.100.28` and the tailnet address, which is
[security.md](../architecture/security.md) §7.1's loopback bind and is carried
by `OLLAMA_HOST` in the plist; `ollama list` showing the store, so `HOME` and
`OLLAMA_MODELS` still point at `/Users/Shared/ollama`; the three models warmed
back at their registry context lengths, largest first, with `keep_alive: -1`;
and all six entrances at 200 afterwards.

## The bench, and two ways it was measuring itself before it measured anything

**`analyse.py` cannot answer "how fast is this model" for a model the task set
has never been run against**, which is the question a candidate raises first and
the cheapest one to answer. `scripts/model-eval/bench_throughput.py` asks it
directly: generation and prompt-evaluation rate at a stated depth, three
repetitions, median.

**It has to recover a known number before it is worth anything, and it does.**
`results.jsonl` puts `gemma4:31b-it-q8_0` between 13.57 and 13.83 gen tok/s on
all sixteen tasks whose depth is under 400, and at 12.71–12.78 on the two near
4400 — flat within a task and flat across depth, which is what a
memory-bandwidth-bound dense model looks like. The bench measured **13.65 at
depth 500 and 12.54 at depth 6407** on the same 0.32.4 the table was produced
on. (The `depth ~710` in `analyse.py`'s heading is the mean depth over all
eighteen tasks, not a depth any prompt had; it is not a target to reproduce.)

**The first version of the bench measured the prompt cache.** Three repetitions
of one prompt reported 199, then 2110, then 2164 prompt tok/s at depth 491, and
69,500 at depth 6398 — Ollama caches the evaluated prefix, so every repetition
after the first skipped prompt evaluation entirely and divided a real token
count by very nearly zero. A four-digit throughput on a machine whose real
figure is three digits is the kind of number that gets written into a design
document. Each repetition now carries a distinct leading nonce, which costs
nothing and makes every one a cache miss.

**The second version measured a model reload.** Ollama keys a loaded instance by
its options, so the first call at a `num_ctx` the model is not resident at pays
a reload: 195 prompt tok/s against a real 200, and at shallow depth a 26-second
wall clock against 9. One discarded call per depth now absorbs it.

**`keep_alive` is sent on every call, and the first run of the bench proved why
it has to be.** Ollama applies its own five-minute default to any request that
omits the field — `.env` states this for `OLLAMA_KEEP_ALIVE` and the platform
sends it on every generation for exactly this reason — so benchmarking a
resident model without it would have silently replaced the deployment's `-1`
pin with a five-minute expiry. It also has to be a JSON *number*: `"-1"` as a
string is parsed as a Go duration and fails with `time: missing unit in duration
"-1"`, which is how this was found, before it had generated anything.

**Measured prompt evaluation is 199 tok/s, and `.env` is doing arithmetic with
117.9.** The `MAX_CONTEXT_LENGTH` comment derives its ceiling as
`65536 / 117.9 tok/s = 556s of prompt evaluation against a 600s read timeout`.
Both inputs have moved: the ceiling is 122880 and `REQUEST_TIMEOUT_SECONDS` is
1200. At the figure measured today a full-context prompt evaluation costs
**617 s against a 1200 s timeout**, so the setting is safe by roughly a factor
of two and the comment explaining it describes a configuration that no longer
exists. Corrected there rather than here.

**The runtime upgrade is close to free on speed, which is what makes the rest of
this comparable.** Same model, same options, 0.32.4 → 0.33.2: 13.65 → **13.89**
gen tok/s at depth 500 (+1.8%), 12.54 → **13.22** at depth 6407 (+5.4%), prompt
evaluation unchanged at ~200. So a difference measured against this baseline
from here on is the model and not the runtime — bought, it should be said, for
the 1.97 GiB above.

## What a full-context request actually costs, and the guardrail it has already outgrown

**A prompt at the ceiling takes 23 minutes to evaluate, against a 20-minute
timeout.** Measured on `gemma4:31b-it-q8_0` at the deployment's own 262144
context: depth **121,892** tokens, just under `MAX_CONTEXT_LENGTH`'s 122,880, at
**88.4 prompt tok/s** — **1,379 seconds** before a single byte could be sent.
`REQUEST_TIMEOUT_SECONDS` is 1200 and reaches the adapter as
`httpx.Timeout(read=1200)`, and prompt evaluation sends nothing, so the read
timeout is what bounds it. A caller sending a prompt the ceiling admits is cut
off at 1200 seconds. From the runtime's own progress log the crossing is at
roughly **110,000 tokens**; above that the request cannot complete.

**The rate is not flat, which is why no earlier figure caught this.** Prompt
evaluation decays with depth on this model — 209 tok/s over the first 10k
tokens, 172 at 25k, 150 at 37k, 105 at 93k, 88.4 averaged over the whole
121,892. Every previous measurement in this repository was taken shallow or on
a different model, so each was locally right and none of them described the
ceiling. Generation decays with it: **6.99 tok/s at that depth against 13.89 at
depth 500**, half.

**The cause is the 2026-08-21 revert, and the ceiling that was raised for a
model that no longer serves.** `MAX_CONTEXT_LENGTH` went to 122880 on
2026-08-17, justified in `.env` and in
[connect-an-agent-client.md](../runbooks/connect-an-agent-client.md) by
`122880 / 711 tok/s = 173 s` measured on `qwen36-35b-a3b-q8`. Four days later
both policies moved back to a dense model that evaluates at 88.4 tok/s at that
depth, and the ceiling was not revisited. The rule `.env` states for itself —
*"raising the context alone gives a ceiling the guardrail admits and the
transport then kills part way through"* — was not broken by raising the context.
It was broken by lowering the throughput underneath it, which the file has no
sentence for.

**Two things soften it and neither closes it.** The platform refuses on its
*estimated* token count, and the estimate for this model uses character widths
calibrated against `qwen36-35b-a3b-q8`, so where the refusal actually falls in
real tokens is not known. And `transport.py` classifies this case as
`runtime_timeout` with the documented remedy *"an immediate retry usually
succeeds, because the prompt is now in the runtime's prefix cache"* — which
`.env.example` contradicts in the same repository, saying the failure "does not
heal, because a cancelled prefill is not kept in the runtime's prefix cache".
One of those two is wrong and this entry did not establish which.

**What it did establish is that residency survives.** Zero evictions across the
whole 1,384-second request, with all three models resident throughout. That
answers one of the measurements [decisions.md](../roadmap/decisions.md) has been
carrying as open since 2026-08-07 — *whether headroom survives a full-context
request* — and the answer is yes, at the ceiling. It does **not** survive above
it: an earlier attempt built a prompt of roughly 179,000 tokens by miscalculating
the tokens-per-word ratio, and Ollama's scheduler logged `model predicted to
exceed available memory, evicting` at `predicted="70.9 GiB"` for
`predicted_num_ctx=262144`, evicting both smaller models before reloading the
target. That is past what the platform will pass on, so it is a property of the
runtime rather than a live exposure — but it is what the failure looks like if
the ceiling is ever raised without re-reading this paragraph.

## Qwen 3.8 27B, measured

**All four figures below are from the same bench on the same runtime**, three
repetitions each, `num_ctx` 16384 so they compare with `results.jsonl`, with the
deployment snapshotted and restored around them.

| | format | quant | resident | gen tok/s @373 | @4558 | prompt tok/s | exact counting | tool call |
|---|---|---|---:|---:|---:|---:|---|---|
| `gemma4:31b-it-q8_0` *(serving)* | gguf | Q8_0 | 33.55 GiB | 13.89 | 13.22 | ~200 | **no** | yes |
| `qwen3.8:27b-q4_K_M` | gguf | Q4_K_M | 16.61 GiB | 23.21 | 22.79 | 219–241 | **yes** | **yes** |
| `qwen3.8:27b-mtp-q4_K_M` | gguf | Q4_K_M | 16.94 GiB | 10.91 | 10.28 | 213–236 | yes | not tested |
| `qwen3.8:27b-mlx` | safetensors | **nvfp4** | 17.22 GiB | **44.50** | **44.10** | 249–251 | **no** | **yes** |

**The MLX build is 3.2x the incumbent's generation and holds it with depth.**
44.50 at depth 373 and 44.10 at 4558 is a 0.9% decay where the incumbent loses
4.8% over the same span and 50% by the ceiling. It runs on a different runner
entirely — Ollama logs `starting mlx runner subprocess` — and the `27b-mlx` tag
turns out to be the **nvfp4** build rather than a repackaged q4, which the tag
does not say and `/api/ps` does.

**MTP is half the speed of the plain q4, not more.** The tag carries a
multi-token-prediction head, and Ollama's 0.32.6 note says the **MLX** engine
uses it for speculative decoding automatically. On the GGUF path there is no
speculation to feed, so the head is weight that gets computed and thrown away:
10.91 against 23.21, with visibly wider spread (9.14–11.16 across three runs
where the plain q4 held 23.16–23.25). Whatever the MTP tags are for, it is not
this runner.

**Two integration questions were open and both now have answers.**

*Exact token counting works, and picking the fast build gives it up.*
`qwen3.8:27b-q4_K_M` declares `tokenizer.ggml.pre = qwen35`, already in
`KNOWN_PRE_TOKENIZERS`, so `GgufTokenCounter.prepare` returns True with no code
change. `qwen3.8:27b-mlx` is safetensors and its manifest carries
`application/vnd.ollama.image.tensor` layers and no
`application/vnd.ollama.image.model`, so `weights_path` raises `BlobNotFound`
and the counter falls back to the character estimate — **cleanly**, which is
what `BlobNotFound`'s docstring promises for "a manifest with no model layer"
and is the first time that branch has been exercised by a real model. The trade
is 44.5 tok/s with estimated counts against 23.2 with exact ones. It is worth
saying plainly that the incumbent is already on the estimate path, so the MLX
build costs nothing that is currently being had.

*Tool calling works on both, thinking on or off.* Given one `read_file` tool and
a prompt that requires it, both returned a single well-formed call with the
right name and arguments and `done_reason=stop`, with `think:false` and with
thinking left on. 0.33.2 ships a dedicated `renderer=qwen3.8` and
`parser=qwen3.5` for it. This is the check `MLX_TOOL_CALLING_VERIFIED` exists to
demand of the other runtime and it was owed to this one too, because `code` and
the whole agent loop rest on it.

**None of them can be added to what is loaded now.** `assert_can_load` compares a
declared `memory_gb` against `51.2 − 39.21 = 11.99 GiB`, and every candidate is
16.6–17.2 GiB resident. Replacing `gemma4-31b-q8` is the only arrangement that
fits, and it fits with room: 33.55 GiB out for 17.22 in leaves 16 GiB where
there is now 12.

**What this does not measure is whether any of them is any better**, and the
repository has a standing rule about claiming that on a stopwatch. The
eighteen-task set in [model-evaluation.md](../model-evaluation.md) and the ten
agent-loop rungs are the instruments for that question and neither was run here.
The bar they set is explicit: `gemma4:31b-it-q8_0` at 94.4% and ten rungs out of
ten, never beaten on a single task by either 2026-08-15 candidate.

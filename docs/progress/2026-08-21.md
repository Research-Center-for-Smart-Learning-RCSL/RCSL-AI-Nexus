## A frontend pass, and a deploy that shipped the defect it was written to fix

The management UI was reviewed for its scrolling behaviour, its copy and its
accessibility, and the three turned out to be one problem seen from different
sides. **The chat transcript never followed a streaming reply.** Tokens arrive
on an external store, which by design does not re-render the component holding
the scroll container, so the effect keyed on `turns.length` fired when a reply
began and never again while it was produced: a long answer scrolled itself out
of view and stayed there until it finished. `useStickToBottom` replaces it and
observes the content element's height rather than inferring growth from state,
which also covers what a message count cannot see — markdown reflowing, a
reasoning block expanding, a late web font. Following is conditional on the
reader being within 64px of the end, because dragging somebody back while they
read earlier output is worse than never following at all.

**The shell scrolled in two places at once.** The header scrolled away on
precisely the screens long enough to need it — Logs, Models, Users — while the
sidebar beside it stayed put, and a page wanting the remaining height competed
with a document scrollbar it could not measure. The shell is `100dvh` with
`<main>` as the only scrolling region now, which is what lets Chat be a genuine
full-height column with one scroll area in it. The sidebar breakpoint moved from
`sm` to `lg` at the same time: between 640 and 1024 a 224px sidebar and a dense
table share a viewport neither fits in.

**Decision records were on the site rather than in these documents.** Refusals
opened with an evening two people lost on 17 August; Chat carried a dated
measurement and its sample count; `agent-setup` and the API reference narrated
what those pages had said on previous days and why they had been wrong. All of
it is gone from what a reader sees and none of the technical content went with
it — the token figures, the app build number, the 286 tool definitions, the
20-to-60% estimator error are all still stated, without the dates and without
the account of how the page came to say them. Every screen's remaining reference
material moved behind an `About this screen` disclosure, one sentence standing
above it, because two to four paragraphs of muted prose ahead of a table is
material read once sitting on top of material read daily.

**And the accessibility defects found on the way.** The navigation rendered a
`<nav>` for the pinned entries and again for every group, announcing six or
seven unnamed landmarks per page; there is one named landmark now and the groups
are lists. A skip link and a focusable `<main>` were absent, so a keyboard
reader crossed the whole sidebar on every navigation. Sortable headers carried
their state in a chevron and nothing else. The column menu claimed
`haspopup="menu"` over a panel of native checkboxes. The header showed
`platform_admin` and `tailnet` verbatim.

**Only the frontend image was rebuilt, which is a deliberate departure from the
routine upgrade in [deployment.md](../architecture/deployment.md) §9.** That
procedure says `docker compose build`, and building both would have put an
unrelated base-layer and dependency rebuild of the backend into a deploy whose
diff is entirely frontend — which is the shape of the 2026-08-20 outage, not a
precaution against it. `docker compose up -d --no-deps frontend-tailnet
frontend-public` recreated two containers; `migrate` did not re-run and no
backend service was touched.

**The image check §9 added on 2026-08-20 was adapted rather than skipped.** Its
question is whether the built image carries the code it is believed to carry,
and for a frontend that is answerable by grep: the new markers present in
`/app`, and the strings the pass removed absent. It paid for itself on the
second deploy, where `grep -r "Uploading..."` returned two files and looked like
a failure — `.` is a wildcard and the file holds `Uploading…`, three bytes of
UTF-8. `grep -F` returned zero. **A check that reports the wrong answer for a
reason unrelated to the deploy is worse than no check, because the instinct is
to trust it the second time.**

**The first deploy shipped a regression in the half of the change it was written
to fix, and a review found it after it was serving.** `useStickToBottom`
attached its `ResizeObserver` from an effect with no dependencies, reading both
refs once at mount. `AppShell` mounts `AssistantDrawer` unconditionally and the
drawer returns `null` while closed, so that effect ran against two nulls,
returned, and never ran again: no observer was ever attached for that component.
The chat panel was unaffected because its container exists from its first
render, and the drawer's own submit-time scroll hid it on any answer short
enough to fit. The commit had also removed the `turns.length` effect that at
least jumped once per completed turn, so the assistant went from following badly
to not following at all. The refs are callbacks now, which ties the observer to
the elements arriving rather than to the component mounting.

**Nothing in the tooling could have caught it, and that is what was fixed rather
than the one line.** `tsc`, ESLint and 374 passing tests were all green against
a drawer that followed nothing. `use-stick-to-bottom.test.tsx` renders a
container that appears after mount, the way the drawer does, and asserts the
observer attached — and attached again after a close and reopen. Both cases fail
against the previous implementation, which was checked rather than assumed.

Three smaller findings from the same review were real. `Jump to latest` used a
smooth `scrollTo`, whose intermediate `scroll` events are indistinguishable from
a reader scrolling up: the first one cleared `pinned`, brought the button back
mid-flight and stopped the observer, and since the animation targeted
`scrollHeight` at click time it landed short on a live stream. Both jumps are
assignments now, which is what the per-token path already did. The always-on row
count added to `DataTable` read `getCoreRowModel()`, which on the Knowledge
screen is one server page, so it rendered `25 rows` directly above that screen's
own `1-25 of 137` — the two-counters-disagreeing failure the comment above its
page size exists to prevent; it is the only table that is both a `DataTable` and
server-paged. And the count read `137 rows` for a filter that matched all 137,
in the one case its own docstring claimed to distinguish.

**The rollback tags were not moved for the second deploy, and this is the second
time that convention has mattered.** `rollback-20260821` names `cdc4a97bd554`,
the build that had served for 32 hours before any of this; the build the first
deploy shipped carries the drawer defect and is not a rollback target. Re-tagging
before every build would have overwritten a good target with a defective one on
exactly the deploy that was fixing something, which is the case §9 already
argues from 2026-07-29.

**Verified after the second deploy.** 376 Vitest tests across 46 files, five
Playwright paths, `tsc --noEmit`, ESLint and a production Next build. Eleven
services running; all six published bindings requested-equals-actual and the
five unpublished correctly `null`; both frontends on `1dc3ab557e39` with zero
restarts and clean logs. `/admin/me` through the frontend answers 401 rather
than 502, so the rewrite reaches its admin entrance. The three entrances serve
the new build byte-for-byte identically, and the copy removed from the pass is
absent from all of them, checked through `llm.rcsl.online` rather than only at
the container port. `check-platform-health.sh` reports `OK`, zero warnings, all
eleven services at 0. `verify-public-entrance.sh` reports **9 passed, 0 failed,
2 skipped**.

**Two things were not done, and neither is a finding.** The two proxy-header
checks on the inference path were left skipped rather than run: they need a
valid API key, that path was not touched by a frontend change, and minting a
production credential for it — audited or, as on 2026-08-20, deliberately
unaudited — is a larger act than the deploy it would be verifying. And the
backend image was not rebuilt, so its digest is unchanged from 2026-08-20.

**`check-platform-health.sh --dry-run` is not a dry run.** The flag is the
environment variable `NEXUS_HEALTH_DRY_RUN=1`, and the argument is ignored, so
that invocation ran the live mailer path. It was benign here — 22:41 is not the
digest hour and the state file was rewritten with the date the morning's digest
had already consumed, so no mail went out and tomorrow's is unaffected — but the
failure mode is a script that looks like it refused to do anything when it in
fact did everything. The argument is worth accepting and rejecting rather than
ignoring.

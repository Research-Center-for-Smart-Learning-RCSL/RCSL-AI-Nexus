## Asked whether the platform draws, and the answer turned out to be about the GPU rather than about the code

The question was whether this deployment has image generation. It does not, and
nothing in the tree is on the way to having it: a search for the obvious names —
`image_generation`, `text-to-image`, `stable diffusion`, `comfyui`, `dall`,
`flux`, `sdxl`, `diffusers`, `automatic1111` — returns three hits at `32b7648`,
and all three are coincidences (a table-state hook, the doc-link checker, an
evaluation harness module).

The survey is [plans/image-capabilities.md](../plans/image-capabilities.md).
This entry records what surprised me while writing it, which was not the answer.

**Three things were already written down, and I only had to find them.** The
capability set says which of its two halves a new name would have to join and
why there is deliberately no third name meaning "either". `model_runtime_port.py`
argues, in the `embed` docstring, against exactly the move a drawing runtime
would tempt someone into — "a second mechanism for naming a model would be a
second place for the registry to be wrong" — which turns "widen the port or open
a new one" from an implementation detail into a decision with a recorded prior.
And `responses/tools.py` has already refused a server-side tool for reasons that
apply verbatim to proxying an external drawing API. A survey that ignored those
three would have proposed something the repository has already argued with.

**`vision` is the interesting finding, not image generation.** It is issuable,
it is shown in the management UI, and the path does not exist: `TextContentPart`
refuses an `image_url` part at the schema, the Ollama adapter has no image code
at all, and the chat composer has no attachment control. The refusal is
deliberate and the docstring names the type that would grow a member when a
vision path arrives. So the platform is selling a capability it cannot serve, and
the only thing keeping that honest is `capability-picker.tsx` disabling names
nothing routes — which stops being true the moment somebody writes a `vision`
policy pointing at a text-only model, since nothing in `ManageRoutingPolicies.save`
checks that a candidate can see.

**What actually blocks drawing is not the missing code.** It is `ARCHITECTURE.md`
§0.2, which says the 40-core GPU serves a single generation at a time and that
`MAX_CONCURRENT_INFERENCE=4` therefore buys queue depth rather than throughput,
and that `NODE_TOTAL_MEMORY_GB=64` is one figure because the memory is unified.
A diffusion model is a second resident competing for that figure and a
GPU-exclusive job stalling every language request behind it. The 2026-08-07
eviction — 55.8 GiB predicted for a context this deployment never sends — is the
measurement of how little slack there is. Generation wants its own node, and
`Node.total_memory_gb`, per-node budgeting and `routing_service`'s
`min_free_memory_gb` are all already built and unused.

So the recommendation is to complete `vision` and defer generation to Phase 3.
Completing `vision` is additive at every layer and, because a VLM turns pixels
into tokens, it leaves `UsageRecord.tokens` meaning what it has always meant —
which is the whole reason it is cheap and generation is not.

**One thing the survey found that is not in the survey's own scope**: the
Responses API's `image_generation` is server-side in the same sense as
`web_search`, and `_assert_no_server_side_tools` only inspects `WebSearchTool`.
Whatever is decided about drawing has to be decided about that tool at the same
time, or a client asking for it gets a model that quietly does not draw.

The survey names three assumptions it could not check here and one live read it
did not make — whether a `vision` policy exists on the deployment today, which
decides whether the risk above is latent or active. None of them needs code to
settle; all of them need the Mac Studio.

## Verified the five plans against the tree, and three of them were describing a repository that no longer exists

A sweep of `docs/plans/` for status accuracy. Two of the five were honest
(the landing page, and this morning's image survey). The other three were not,
and the interesting part is that they were wrong in opposite directions.

**The two UI packages were finished and still said "proposed".** All twelve
ranked items are in the tree, landed through `codex/ui-optimization-plans` and
merged at `07f09d5`. Both plans now carry an item-to-commit table. Their
"explicitly frozen" clause held exactly: no file under `entry-transition*` has
been touched since 2026-08-30, which is the one thing both plans asked for and
the easiest to violate by accident.

**The compaction plan said "planned, not implemented" while most of it was
live** — and the part that is missing is the part the plan cared most about.

Three things were found by reading, not by running:

1. **Tier 2 and the prefix-hash cache are unreachable.** `compaction_tier2.py`
   and `compaction_cache.py` implement §5.3 and §5.4 faithfully. The
   orchestrator calls Tier 2 only when `self._summarise_fn is not None`, and
   `build_route_chat_request` passes none of `summarise_fn`, `compaction_cache`
   or `compaction_lock`. So 379 lines of it have never run outside a hand-built
   orchestrator, and a conversation tiers 0 and 1 cannot rescue is refused
   today exactly as before.
2. **The disclosure is one third built, and four places in the tree said
   otherwise.** §3 is the one place the plan amends the request: on by default,
   and never silent. `usage_records` carries the tier; nothing carries it into
   the response or the admin UI. Meanwhile `api_key.py` asserted the disclosure
   "is always present when compaction fires", the migration said it "ships
   together with the disclosure, never before it", and both the assistant
   prompt and the proposal policy told operators the oldest turns get
   summarised — describing, to the person choosing the setting, the one tier
   that never runs. All five now say what is true, and §9 of the plan records
   the gap rather than quietly closing the wording over it.
3. **There are no tests for any of it.** The sixteen "compaction" hits under
   `backend/tests` are all the API-key switch. Tiers 0 and 1 are live in
   production with nothing asserting what they drop.

**And item 2 — the one-value fix — had reached nothing.** `queue_wait_seconds`
was raised from 120 to 1200 in `runtime.py` on 2026-09-05, with the reason in
its docstring. `.env` still had 120, `.env.example` still had 120, and the
deployment configuration table still documented 120. A default is only a
default: every one of those three overrides it, so the change that was "most of
what two people using this hard at once actually needs" had been sitting
inert for two days. All four now agree; it takes effect on the next restart.

The lesson worth keeping is narrow. A Status line at the top of a plan is the
first thing anyone reads and the last thing anyone updates, and the failure is
not symmetrical: a plan that says "proposed" when the work is done costs a
re-reading, while one that says "not implemented" when the switch is live in
production costs somebody a wrong belief about what their API key does.

## Wired the compaction that was written and unreachable, and the first test found the bug the reading had not

Two of the three gaps from the sweep above, closed. The disclosure is the one
left open, because how a response carries it is a decision rather than a task.

**Tier 2 now has collaborators.** `build_route_chat_request` passes
`summarise_fn`, `compaction_cache` and `compaction_lock`; the two untyped
parameters are typed; the lock is built once per process on `app.state` in both
composition roots. That last one matters more than it looks: the dependency is
per-request, so a lock built inside it would have been a new lock every request
and would have serialised nothing — the guarantee would have read as present in
the code and been absent in the process.

The summariser resolves `assist` through `RoutingService` **per call**, not per
request. Per request would put a routing read and two table scans on the front
of every chat request to prepare something Tier 2 rarely reaches, and would pin
the policy until the next restart. There is no fallback to the serving model
when `assist` cannot be routed, because §5.3 chose `assist` precisely so a
summary never competes for the slot the caller is waiting on — a fallback would
undo that quietly on the day the policy is missing. A summariser that raises
leaves the request meeting the same `ContextTooLongError` it would have met with
compaction switched off, which is a refusal that names the ceiling.

**The cache had never been able to hit, and no amount of reading it would have
said so.** The second test written against Tier 2 asserted the property §5.4 is
built on — the same conversation, one turn later, must not summarise again — and
it failed. The prefix was `len(messages) - _KEEP_RECENT`, a boundary measured
from the end of a conversation that grows by two messages every turn, so every
turn hashed a different key and every turn summarised. The module is a faithful
implementation of §5.4 that delivers exactly the outage §5.4 exists to prevent.

The fix is what §5.4 already said in words — "summarised once and reused until
it grows past the next threshold" — so the boundary is floored to a multiple of
ten messages and holds still between thresholds. The lesson is narrow and worth
keeping: prefix stability is a property of what the client sends, and the plan
was right about that. It is not automatically a property of a boundary computed
from the length of what the client sends.

**Twenty-two tests, and the last two are about the wiring rather than about
compaction.** That ordering is deliberate. The modules were correct; a test of
the modules would have passed on 2026-09-05 and every day since while nothing
ran them. So the file ends with a test that builds the composition root and
asserts all three collaborators arrive, and one that reads both entrance modules
for the lock — the assertions that would have caught the actual defect.

**And group T finally has its cross-turn dependency**, which model-evaluation.md
§7.6 has wanted since the group was written and which §7 of the plan named as
the acceptance test for compaction. `recall_across_turns`: fifteen turns, two
figures given once at turn three inside a question about something else, asked
back separately at turns twelve and thirteen and as their product at turn
fifteen, none of the three questions carrying its own answer.

Asking for the parts before the product is the part that earns its keep here. A
summariser told to preserve figures tends to keep the one its sentence was about
and lose the one in the subordinate clause, and that failure is invisible to a
single question about the total. Turn fourteen is the control, on the group N
pattern: it asks about something the student never said, where producing a
number is the failure — without it, a model that had lost the history could pass
by inventing and one that never invents could pass by declining everything.

A first draft of it scored 0.95 for a model that had lost the entire early
history, because fifteen `NEXT:` trailer checks drowned the one check that
mattered. The trailer is now checked on three turns. Reference 1.00, the decayed
answer 0.40, decline-everything 0.70. Validated in both directions, **not
calibrated**: no model has answered it yet, so §4.3's band says nothing about it.

Suites after all of it: 1,024 backend unit (up 22), 124 integration against a
throwaway Postgres, 483 frontend, 41/41 scorers validated, and no drift in the
generated API types.

## The disclosure, and the surface §3 assumed already existed

The third gap closed. §3 of the compaction plan is the one place it amends the
request — on by default, and never silent — and it asks for three surfaces: the
response, the usage row, and the admin UI. Only the row existed.

**Which channel was never really the question.** This repository had answered it
three times before compaction existed — `X-Capability-Defaulted`,
`X-Dropped-Tools`, `X-Knowledge-Sources` — and the first is the same problem
exactly: an opt-in per-key setting that removes a refusal. The roadmap wrote the
reasoning down when it shipped, that the evidence has to outlive "both a header
the client may not read and a log line that rotates". So `X-Context-Compacted:
tier=N`, in the same helper as its three predecessors. A body field is what
`route.py` already refuses in terms; a system message prefixed to the model's
output would enter content the caller replays, and become part of the prompt
compacted on the next turn.

**What was genuinely in doubt was whether a header could carry it at all**, and
the answer was already in the tree for a different reason. Compaction happens
inside the concurrency slot, and headers close when the body opens. But both
routes call `sse.prime()` before constructing the response — "so a routing
failure is a status code rather than a 200 carrying an error event" — and
priming pulls the first chunk, which is downstream of the slot. There is a
window where the fact is known and the headers are not yet written, and it
exists because of a decision taken about error handling. `compaction_header()`
is read after priming while `capability_defaulted_header()` beside it is read
before; the asymmetry is commented at both call sites.

**The admin UI needed a screen that did not exist.** `/admin/usage` is
aggregate, and the only per-request view was `prompt_logs`, which exists solely
while a debug window is open. So `usage_records.compaction_tier` was written by
the gateway and read by nothing. Worse: that table had *never* had a reader
returning a row — every consumer since the first migration was an aggregate, so
the platform recorded what each request did and could show nobody any of it.
"Which request was the 413 the integrator is quoting?" was answerable only from
a log line that rotates.

Now: a compaction card on the usage screen (a ratio, not a count, and rendered
at zero so "not firing" can be told from "no such card"), `GET
/admin/usage/records` with a `compacted` filter, and a marker on the transcript.
Listing that table across accounts is audited as `usage.read_any`, on the line
`refusal.read_any` already draws — counts per hour describe a tenant, one row
per request describes a person.

**The transcript was not in §3's list and should have been**, and the frontend's
`api-contract.ts` is what said so: after the summary schema was widened, the
transcript response was the one shape that disagreed with its zod type. It is
the only place a person reads the prompt itself, and after a compaction that is
not the prompt the caller composed — the quietest possible place for the
reduction to hide.

One detail recurs at every layer, and it is the same mistake each time: **tier 0
is a compaction.** SQL `is_not(None)`, Python `is not None`, React `!== null`,
zod keeping the zero. A truth test anywhere in that chain hides the cheapest
tier — the one a reader is least likely to expect.

Suites: 1,035 backend unit, 128 integration, 485 frontend, `tsc --noEmit` clean,
generated types with no drift, and `a2f7c31b9e84` applied and rolled back
against a throwaway Postgres.

## The halving is not what the plan says it is, and one registry row is eight times too large

Two of the compaction plan's open items, taken on the machine itself. Ollama
0.33.2 is up, so both were measurable here rather than deferred.

**§8 item 3 asked whether `--context-shift` *is* the `num_ctx / 2` halving.**
That framing turned out to be the wrong question, and the right one was cheap.
Four probes against `qwen2.5:7b` resident at 32768, each prompt counted exactly
by the platform's own GGUF tokenizer rather than estimated:

| counted | `prompt_eval_count` | |
|---:|---:|---|
| 26,624 | 26,602 | whole prompt read, 81% of `num_ctx` |
| 31,506 | 31,484 | whole prompt read, 96% of `num_ctx` |
| 34,816 | 16,386 | truncated to `num_ctx / 2` |
| 66,328 | 16,386 | truncated to `num_ctx / 2` |

**A prompt that fits inside `num_ctx` is read whole. A prompt that exceeds it is
truncated to half.** §2.5 generalised the second half of that into a cap on
every prompt, and the platform's entire input ceiling rests on the
generalisation: `max_context_length = 122880` sits below half of 262144 rather
than below 262144. So the deployment may indeed be running at half the context
it paid for — item 3 was right about the prize — but the cause is not context
shift and the remedy is one configuration value rather than a runtime patch.

I nearly recorded the opposite. The first probe came back 26,602 and I read it
as a refutation of the halving; the number is only meaningful beside an exact
count of what was sent, and counting it is what turned "the rule is wrong" into
"the rule has a boundary". The second probe, deliberately above `num_ctx`,
reproduced 16,386 exactly.

**And the 2026-09-03 secret-word evidence does not survive.** That probe read
the model's failure to see a first-line marker as proof the beginning had been
dropped. My first probe put three markers in a prompt that was demonstrably not
truncated, and the model reported two and missed the first. A 7B model missing a
marker at the head of 26,000 tokens of filler is an attention failure and is
indistinguishable from truncation by that method. The token counts are the
evidence; the markers never were.

Nothing should move yet: all four measurements are one small model at 32768
through `/api/generate`, and the incumbent at 262144 on `/api/chat` is what a
ceiling change would actually rest on.

**Item 4 was two questions wearing one coat.** The "three disagreeing memory
figures" are not three views of one model: `memory_gb = 41` and `/api/ps`'s
33.55 GiB are `gemma4:31b-it-q8_0`, while the 55.8 GiB prediction was for
`gemma4:31b-it-qat` — a different build, registered separately at
`memory_gb = 18`.

What the reconciliation did turn up is worse than the puzzle it dissolved.
**`qwen7b` is registered with `context_length = 262144` and the model's own
maximum is 32768** — its GGUF says `qwen2.context_length = 32768`, and the
running `llama-server` carries `-c 32768`. `_refuse_what_this_target_would_truncate`
refuses at half the *registered* figure, so `assist` refuses at 131072 against a
model that truncates anything over 32768 down to 16384. A prompt between roughly
32,769 and 122,880 tokens on `assist` passes the global ceiling and the
per-model guard and is silently cut by the runtime — which is exactly what that
guard was added on 2026-08-17 to prevent.

It was theoretical while `assist` carried only the management assistant, whose
prompts peak near 4,000 tokens. **Tier 2, wired this morning, is what makes it
reachable**: it sends the oldest prefix of an over-long conversation to that same
model, and that prefix is large by construction. Nothing has been observed
failing; this is read out of the two findings together, and §9.7 of the plan
sets out the three candidate fixes and why they are not alternatives.

Both probes ran against the live deployment with `keep_alive: -1` and the
resident `num_ctx`, so no model was loaded, evicted or unpinned.

## The registry row, and teaching the platform to read what the model says about itself

Both halves of §9.7, taken together because they are the same defect from two
sides: the data was wrong and the code trusted it.

**`qwen7b` is now registered at 32768.** That is what its GGUF declares and what
its running `llama-server` already carried, so nothing reloaded and no residency
changed. What changed is the guard: `_refuse_what_this_target_would_truncate`
refuses `assist` above 16384 now rather than above 131072, which is the
protection 2026-08-17 added and a registration eight times too large had been
quietly holding open.

**`TokenCounterPort` gained `native_context_length`.** It reads
`<family>.context_length` out of the same GGUF header the vocabulary comes from
— a header scan that skips every value it is not asked for, cached per
reference. On that port rather than a new one for the reason
`ModelRuntimePort.embed` gives for living beside `generate`: a second reader of
the same file would be a second place for the answer to be wrong.

Tier 2 now takes the **smaller** of the registered and declared figures, and
where a counter exists it counts the prefix before sending it and raises rather
than handing the runtime a prompt it would cut in half. That refusal becomes the
ordinary context refusal, which is exactly where such a request sat before Tier
2 existed — the feature declines to act rather than acting on a prompt it cannot
honestly summarise.

**Then every row was audited against its model**, which is the part worth
keeping:

| alias | registered | declares |
|---|---:|---:|
| `embedder` | 8192 | **2048** |
| `gemma4-31b` | 131072 | 262144 |
| `gemma4-31b-q8` | 262144 | 262144 |
| `glm47-flash` | 32768 | 202752 |
| `qwen36-35b-a3b-q8` | 262144 | 262144 |
| `qwen7b` | 32768 | 32768 |

Registering *below* a model's maximum is a deliberate choice and four rows do
it. Registering above it is a defect, and after today exactly one row still
does: the embedder, by four times. It is left alone because lowering it changes
what the knowledge base accepts at ingestion, which is a different decision from
this one.

The durable fix is still not done. Nothing stops the next registration
overstating its model — the audit above was a script run by hand, and the reader
that makes it possible now exists on a port anything could call.

## The durable half: comparing the claim against the model at the moment of loading

The registration is a number an operator typed; the GGUF header is the fact.
Nothing compared them until today, which is how `qwen7b` sat at 262144 against a
declared 32768 for as long as it took somebody to read `/api/ps` beside the
`models` table. Loading a model now does the comparison and says so.

Three choices in it, and each was a fork:

**Before the runtime call, not after.** `_prepare_token_counter` deliberately
runs after every write, so a vocabulary that cannot be read never unwinds a load
that already happened. This one is the opposite case: the figure it warns about
is the one about to be sent as `num_ctx`, and a warning that arrives after the
runtime has reserved for a context the model cannot hold describes something the
operator can no longer choose against — which is exactly the 2026-08-07
eviction.

**One direction only.** Registering *below* the declared maximum is the ordinary
deliberate choice, made to bound memory or to keep a model inside the platform
ceiling, and four of this deployment's six rows make it. A warning that fired on
those too would be one an operator learns to scroll past, and the next real
overstatement would go with it.

**Warn, not refuse.** A refusal would make a wrong number in a table unable to
serve at all, on the strength of a file read that fails for reasons having
nothing to do with the number: a missing mount, an unpulled reference, an
architecture spelling the key differently. `None` from that reader means cannot
say, and cannot-say must never be what stops a model loading. The load is the
operator's; this makes sure they are told.

That closes §9.7 in full — the data was wrong (the row), the code trusted it
(Tier 2), and nothing checked (this). Four tests pin it, including the one that
asserts silence in the safe direction, because that is the half a warning
usually gets wrong.

## The embedder row, and the probe that found the ruler was 2.2x wrong

**`embedder` is now 2048**, matching what its GGUF declares. It had none of
`qwen7b`'s exposure and the difference is worth recording rather than assuming:
chunking is by characters at 1200, about 300 tokens, so nothing ingested has
ever approached either figure; `ModelRuntimePort.embed` takes no context length;
and the chat guard never sees an embedding request. The number reached exactly
two places — the `num_ctx` sent at load, which Ollama was already clamping to
2048, and the models screen. Correcting it changed no behaviour and removed a
false number. **No row now overstates its model.**

**Then the ceiling probe, which did not answer the question it was asked.**
160,218 counted tokens to the incumbent at `num_ctx = 262144` through
`/api/chat`, ten minutes of prefill, and `prompt_eval_count = 70,749` — neither
the whole prompt nor `num_ctx / 2`. 453,928 characters over 70,749 tokens is
6.42 characters per token, an ordinary density for repetitive English, against
the 2.83 the platform's counter had claimed.

The prompt was never truncated. **It was never 160,218 tokens.**

Calibrated against the runtime's own `prompt_eval_count` on three texts, the
counter reads 2.23x, 2.48x and 1.42x too high on `gemma4:31b-it-q8_0`.
`qwen2.5:7b` was the control and came back at 1.08-1.11x — a constant ~21-token
offset, which is this platform's chat template rendering slightly longer than
Ollama's rather than a scaling error. The two take different paths: `qwen2`
declares `tokenizer.ggml.model = gpt2` and goes through BPE; `gemma4` declares
`llama` and goes through Unigram. Only Unigram was wrong, and **it had no test
at all.**

The cause is one line, in two languages. A GGUF's `scores` for a `llama`-type
vocabulary are ordinal ranks — this one carries exactly 0.0 to 262143.0 — and
Unigram needs log-probabilities. The conversion was `log((N - rank) / N)`:
order-preserving, and crushing the whole vocabulary against zero, with rank 1000
at -0.0038 and rank 20000 at -0.079. Unigram maximises the *sum* over a split,
so when every score is that close to zero, breaking a word into three tokens
costs almost nothing. `-log(rank + 1)` spreads the same ranks over twelve nats;
counts land at 1.03-1.10x, matching the control.

Both backends carried it — the Python builder and the Rust extension have the
same expression, and swapping them gave identical wrong answers, which is how I
knew it was the vocabulary and not the encoder. Both are fixed and the wheel is
rebuilt. **The running containers still hold the old wheel; this reaches the
deployment on the next image build.**

**What it cost.** The incumbent serves `chat` and `code`. At a 122880 ceiling
counted this way, callers were refused at roughly 55,000 real tokens against a
model that reads 262144 — and that ceiling had been raised three times, in
August, chasing agent clients who kept hitting it. Compaction fired on prompts
that were never near a limit. The error was in the over-counting direction, so
nothing was ever served from a prompt the runtime had truncated: what was lost
is capacity, not correctness.

**The ceiling stays where it is.** Every input to that decision — how much
context real traffic uses, how close it runs to the limit, what a raise buys —
was measured with this ruler, and none of those numbers means what it said. The
right order is to let the corrected counter run against real traffic first.

Two tests now cover the path that had none, and both fail under the old mapping.
Getting the second one to fail took two attempts: at toy scale the defect does
not reproduce, because `log((N - rank) / N)` only crushes the gaps when N is
large, and the first version of the split test passed under both mappings while
claiming to test the difference. A test that asserts less than it says is worse
here than no test, since this file exists because an untested path shipped a
twofold error.

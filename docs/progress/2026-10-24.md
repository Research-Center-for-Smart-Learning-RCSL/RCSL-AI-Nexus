# 2026-10-24

## #61, first package: the maintenance hold closes access

The first of #61's six packages (P1 and P2 of the plan on the issue). It adds
the hold and closes every way in; it does not yet stop work already running
in the runtime, release models, or restore them. Entering is therefore behind
`MAINTENANCE_ENABLED`, off by default and off in production.

**What a hold does now.**

- One row, `maintenance_control`, read by every process. Only the admin
  accounts can write it; the gateway can read it and nothing more
  (`test_db_role_grants.py`).
- Every entrance refuses everyone except platform administrators (`role ==
  admin`), with 503 and the code `maintenance`, and `Retry-After: 60`. A tenant
  administrator is held out like any other role.
- Every non-admin local session dies at entry and stays dead after reopening.
  Each session records the maintenance epoch it was issued in; an entry opens
  a new epoch. A login that read the epoch just before an entry committed
  carries the old one and dies the same way. Sessions written before this
  change decode as epoch 0, so deploying it signs nobody out.
- A login begun before the hold cannot be finished during it, by TOTP or by
  recovery code. The password step answers as before, so the hold does not
  reveal which accounts exist.
- Tailnet users have no session; the hold refuses their identity on each
  request. Their Tailscale accounts are untouched.
- Every API key, an administrator's included, is refused, `/v1/models` as
  well. No key is revoked; the same key works once the platform reopens.
- Administrators keep the management screens and lose the models: admin
  chat, the assistant, knowledge search, ingestion, reindexing and every
  model lifecycle action answer 503 `maintenance`.
- Detached indexing stops at its next embedding batch. The extracted text is
  kept, so a reindex after reopening does not parse the file again.
- The residency reconciler is suspended. It does not rewrite the desired set.

**API.** `GET /admin/maintenance/status` needs no sign-in and says only
whether the platform is closed, the message and the expected return time.
`GET /admin/maintenance`, `POST /admin/maintenance/enter`, `POST
/admin/maintenance/reopen` and `PUT /admin/maintenance/message` need the new
admin-only scopes `maintenance:read` and `maintenance:write`, and the live
admin role. Entering and reopening twice are idempotent; only a message edit
is revision-checked.

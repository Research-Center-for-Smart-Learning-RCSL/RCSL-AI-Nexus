## Took the platform down on purpose, and two of the six daemons did not go

The platform was shut down deliberately — services and the host-layer background
jobs — and brought to a verified stop. The runbook written from it is
[runbooks/planned-shutdown.md](../runbooks/planned-shutdown.md). This entry
records what the shutdown found, which was not what it set out to do.

**`launchctl bootout` stopped four of the six jobs and silently failed on two.**
`bootout` returned zero and printed nothing for all six, and after it,
`colima` and `socat-forwards` were still doing their work: `docker info`
answered, and three socat processes were still forwarding the tailnet ports.
The cause is the same for both — the processes that do the work had already
reparented to PID 1, so what `bootout` removed was the launchd job registration
and not the running program. `colima stop` and killing the socat supervisor
shell were what actually stopped them. `ollama`, `host-metrics`, `backup` and
`reconcile-port-bindings` went down on `bootout` alone.

The lesson is narrower than "bootout is unreliable" and worth stating precisely:
**for a long-lived job that spawns a supervisor or a VM, the exit status of
`bootout` is not evidence that anything stopped.** The evidence is `ps`. The
runbook's §4 is five commands that check processes and listening ports rather
than trusting any command's return value, and it exists because of this.

**The check that would have caught it earlier could not run.**
`sudo -n launchctl print system/<label>` needs a password on this machine, so a
non-interactive check cannot ask launchd what it still has loaded. That left the
process table as the only source of truth available to the session doing the
shutdown — which turned out to be the right source anyway, since a job can be
gone from the domain while its process keeps running, and that is exactly the
state that occurred.

**There is no maintenance mode for the health check, and this was worth
confirming rather than assuming.** `check-platform-health.sh` mails on every
state change to two recipients, and a planned outage is a state change. A search
for a mute, snooze, or maintenance-window mechanism found none — so the only
choices are to accept the alert mail or to `bootout` the health check for the
duration, and the second one trades the noise for a window in which nothing is
watching. The runbook makes the decision an explicit first step rather than
something discovered after the mail has already gone out.

**Shutting the platform down does not survive a reboot, and that is the
`boot-recovery-acceptance.md` design working as intended.** The six plists stay
in `/Library/LaunchDaemons`, so the next boot loads `colima` and then
`reconcile-port-bindings`, which compares the running set against
`EXPECTED_SERVICES` and runs `docker compose up -d` on whatever is missing
(`lib/reconcile/expected_bindings.sh:40`). For an unplanned outage this is the
whole point. For a planned one it is a trap: **shut the platform down, reboot,
and you have restored it.** `bootout` and `disable` are not substitutes for each
other — the first does not affect the next boot, the second does not stop what
is running — and a shutdown meant to outlast a reboot needs both.

The same property is a recovery path, which is why the runbook's troubleshooting
table ends with it: as long as nothing was `disable`d, `sudo reboot` brings the
platform back along the path that has already been acceptance-tested, and when a
manual restore is stuck under time pressure it is usually the faster move.

# 2026-10-25

## #61, third package: the node agent fences the hold and can stop the runtime

P3 of the plan on #61, stacked on the first package (#77). It adds what the
node and the host need for a forced entry and a verified restore. It does not
yet use them. Entering stays behind `MAINTENANCE_ENABLED`, off by default and
off in production, and the coordinator that drives these pieces is P4.

**On the node agent.**

- **Promotion reads the hold in the database.** An entry takes an advisory lock
  exclusively before it closes the platform. `accepted → running`, the point
  where a send is authorised, takes the same lock shared and reads the hold.
  - Any promotion that commits has therefore read the platform open after every
    entry that committed before it.
  - None can read "open" and commit after the platform closed.
  - A refused attempt becomes `cancelled_unsent` with
    `maintenance_before_send`.
  - The gateway hears 503 `maintenance`, not `overloaded`.
- **A frozen gate.**
  - A promotion that finds the hold closed freezes the gate in the new
    `maintenance` state. So does the watchdog, which reads the hold every tick,
    and so does start-up.
  - A frozen gate stays `maintenance` through reopen, drain and block until the
    hold lifts. It then returns to whatever it would otherwise be: drained,
    blocked or serving.
  - An agent started during maintenance never serves.
- **The final send barrier.** A task promoted just before the freeze is
  withheld at its last in-process step, before the runtime sees a byte, and
  becomes `cancelled_unsent`.
- **Interrupt.**
  - `POST /v1/maintenance/interrupt` cancels every relay still talking to the
    runtime. It acts only for the epoch the database says is closed.
  - Each cancelled attempt becomes `outcome_unknown` with
    `maintenance_interrupted`, which is truthful, and the node stays blocked
    after the hold lifts until a verified reset.
  - The report keeps sender quiescence apart from settlement, so a database
    outage cannot hold up the runtime's stop.
- **A separate control token.**
  - `node_agent_control_token` is a second secret, and only the agent mounts
    it. It must differ from the data token.
  - It is required by drain, resume, block resolution, interrupt, runtime
    control and the resolve CLI.
  - The gateway holds only the data token, which those routes refuse.

**On the host.**

- **The root runtime supervisor.** `scripts/host/runtime_supervisor.py` runs
  as `online.rcsl.runtime-supervisor`.
  - It takes one of three fixed actions on `online.rcsl.ollama`: stop, start
    and restart.
  - It acts through request and receipt files, as the agent already does with
    the witness.
  - A stop unloads the job, so `KeepAlive` cannot respawn it. It then ends the
    daemon and every model runner, signalling a process only after re-reading
    its unchanged PID and start time, and verifies a fresh scan is empty.
  - Each request runs at most once and leaves a receipt.
- **Supervised reset.** `resolve reset` clears an `outcome_unknown` block in
  one command (the reset action #49 §5 handed to this issue).
  - It uses the same ordered witness evidence as `start` and `complete`, with
    the supervisor's restart in between.
  - The receipt is recorded beside the two witness answers.
- **Installation and host acceptance** are in
  [runtime-supervisor.md](../runbooks/runtime-supervisor.md).

## The runtime supervisor passes host acceptance

Installed on the Mac Studio after P3 was deployed, then run through the
acceptance in [runtime-supervisor.md](../runbooks/runtime-supervisor.md), with
no traffic, on Ollama 0.40.8. Two faults surfaced first and are fixed on main.

- **It crashed on import.** The LaunchDaemon runs `/usr/bin/python3`, the
  Command Line Tools' 3.9, and the script used `@dataclass(slots=True)`, which
  3.9 lacks. Its tests had passed on the backend's 3.12. A new CI job,
  `host-python`, now imports every script under `launchd/` and `scripts/host/`
  and runs their tests on 3.9.
- **It could not see the model runners.** It counted only processes named
  `ollama`, but Ollama 0.40 runs each model in a `llama-server`. A stop would
  neither have waited for the runners nor noticed one that survived. Found by
  comparing the host's `ps` with the test's fake before the first restart.
  `--process` now repeats and the plist names both.

**The restart.** `drain`, then `runtime restart`, then `resume`.

- **The receipt is `ok`.**
  - `before` lists the daemon and both runners, one per resident model.
  - `after` lists only the new daemon.
  - The steps are `bootout`, `unloaded`, `stopped`, `bootstrap`, `started`.
    No signal was needed: the runners exited with the bootout.
- **Nothing of the old instance is left.** `ps` showed only the new daemon,
  and the account's system agents (`cfprefsd`, `distnoted`) were untouched.
- **Service came back.** The reconciler reloaded both resident models, with
  Gemma at its registered 262,144 context, about a minute after `resume`. An
  authenticated chat request through the public gateway then answered 200,
  with a temporary key that was revoked afterwards.

**Timings, measured for #61's deadlines.**

| Step | Time |
| --- | --- |
| `bootout` to `unloaded` | 0.65 s |
| `bootout` to `stopped`, with both runners gone | 0.71 s |
| `bootstrap` to `started` | 0.57 s |
| Request written to receipt read, through the CLI | 2.8 s |
| `resume` to the full resident set reloaded | about 60 s |

The stop is fast because nothing was generating. A runner busy with a long
generation may take longer to exit, so the deadlines should leave room for
the SIGTERM step, not just these numbers.

## #61, fourth package: the coordinator that carries an entry out

P4 of the plan on #61. Entering maintenance now does more than close access:
it releases every runtime, and records what each one held so P5 can restore
it. Entering is still behind `MAINTENANCE_ENABLED`, off in production, until
P5 restores the snapshot and both pass on the host.

**The entry.**

- **Refused before anything closes** with `maintenance_unsupported` when node
  agents are off or any node has no agent. Such a runtime could not be
  interrupted or released, so the platform would be closed to users while it
  kept working.
- **One transaction.** The hold closes and records an operation with one step
  per node, in new tables `maintenance_operations` and
  `maintenance_node_steps`. The gateway may not read either: they hold
  snapshots and reset evidence.

**The coordinator** runs in the tailnet admin, beside the heartbeat, and is
the only process besides the agent that mounts `node_agent_control_token`.

- **Each node, in order, each result written before the next call.**
  1. *Interrupted.* The agent freezes for the epoch and cancels every sender.
  2. *Snapshotted.* What the runtime actually holds, from `/api/ps`: name,
     digest, size and loaded context. Written once and never replaced, so a
     retry cannot overwrite the original with a half-emptied runtime. A
     runtime that cannot be observed after three tries is released anyway,
     and the step says there is no snapshot and why; it is never recorded as
     empty.
  3. *Reset.* A new agent route, `POST /v1/maintenance/reset`. It takes the
     witness baseline, has the supervisor restart the runtime, takes the
     second answer, and resolves every `outcome_unknown` that evidence covers.
     It does not reopen the gate.
  4. *Verified.* A fresh observation of the new runtime holds no model.
- **Nothing is held across a call to a node.** Every read and write is its own
  short transaction.
- **Ownership is a lease, and every write is fenced on it.** A second
  coordinator takes over only after the lease expires, and a stale one cannot
  write over its successor. Two coordinators started together restart the
  runtime once.
- **A failure keeps the platform closed.** A step that keeps failing stops as
  `failed` with its error, and the operation fails once no step is running.
  `POST /admin/maintenance/retry` runs the failed steps again from the phase
  each reached. A supervisor that reports a failed restart fails the step at
  once, and the retry is a new restart.
- **A hold lifted or superseded** abandons the entry untouched.
- **Audit.** `maintenance.node_cleared`, `node_failed`, `entry_cleared`,
  `entry_failed`, `entry_abandoned` and `retried`, under the coordinator's own
  subject.

**The reset is resumable.**

- The caller names it, and the supervisor request carries the same id.
  Asking again returns the recorded outcome instead of restarting twice.
- The baseline, the receipt and the outcome are written to the node's audit
  as they happen. A reset asked again after an agent restart continues from
  the recorded baseline.
- Without a witness answer, the runtime is still released. The unknowns stay,
  with `accounting: unresolved` and the reason.

**`GET /admin/maintenance`** now carries the latest operation: each node's
phase, status, attempts, error, snapshot, interrupted attempts and
accounting. That is the "models released" half the UI must show apart from
"access closed".

**Deploying it** needs the control token mounted into `admin-tailnet`
(`docker-compose.node-agent.yml`) and the migration. Recreate `admin-tailnet`
so it reads the secret.

**Not yet done** after P4 is P5, below.

## #61, fifth package: restoring the snapshot before reopening

P5 of the plan on #61. `POST /admin/maintenance/restore` puts back what the
entry released and reopens the platform only once every node verifies.
Entering stays behind `MAINTENANCE_ENABLED` until the console (P6) and host
acceptance ([maintenance-mode.md](../runbooks/maintenance-mode.md)).

**When a restore is allowed.**

- Only after the entry under the current hold has succeeded, with a snapshot
  for every node and every node's unknowns resolved.
- Otherwise it is refused with the reason, and reopening without a restore
  stays available.
- Pressed again, it returns the running restore.

**What it does on each node.** A `restore` operation holds a copy of the
node's snapshot, which never changes.

1. *Loading.* One model at a time, largest first, as the reconciler restores
   (#49). The whole node is observed again after every load, because a large
   load can evict a sibling restored before it. An evicted model is loaded
   again, bounded by the reconciler's repair rounds.
2. *Loaded.* Every saved model is resident with its recorded digest and
   context, and nothing else is. A model the snapshot did not hold fails the
   node.
3. *Probed.* Each model answers a bounded check: a vector from an embedding
   model, a token from any other. The check is sized with the context the
   model was loaded with, so it cannot reload it. The node is observed again
   after.
4. *Verified.* Observed once more.

**The serving commit.**

- Once every node is verified, every node is observed again, fresh.
- Then one transaction ends the restore and lifts the hold, at that epoch only.
- A node that changed meanwhile is restored again, and nothing reopens.

**On the node agent: the only way past a frozen gate.**

- `POST /v1/maintenance/restore`, control token only, runs a `load` or a
  `probe` (a new operation kind).
- It needs the hold closed at the epoch named, both in the database, read at
  promotion under the entry's fence, and in the frozen gate.
- It keeps the gate frozen, so traffic is still refused while it runs, and
  only it passes the final send barrier.
- The model must be registered on the node. The runtime must hold the
  snapshot's digest, and the context must be the one it was loaded with.
  Otherwise `model_not_on_node`, `revision_mismatch` or
  `context_length_mismatch`, which fail the node at once.

**Tests.** The coordinator's restore covers six cases:

- largest first, with probes, then reopen;
- an evicted sibling reloaded;
- a model the agent will not restore;
- a model the snapshot did not hold;
- a node that changed before the commit;
- an empty snapshot.

The dispatcher's exception is tested against the wrong epoch and a lifted
hold, and traffic stays refused while it runs. End to end, on Postgres, an
entry and a restore run against a running agent: the models come back with
their contexts, largest first and probed, the operations are recorded under
the epoch, and the gate serves again after the commit.

**Not yet done** after P5 is P6, below.

## #61, sixth package: the console

P6 of the plan on #61. The maintenance console now drives the whole cycle; it
used to say that closing did not yet interrupt or restore anything.

- **Three milestones, kept apart.** Access closed, runtimes released and models
  restored. The first happens at once; the other two take time and can fail.
- **Each node's progress** through the hold's entry or restore:
  - its phases as a trail, with the current one marked and a failure in red;
  - its snapshot, as model and context, or why there is none;
  - how many running requests were interrupted, and whether they were
    resolved;
  - its attempts and its last error.
- **Restore and reopen.** Disabled until a restore could put everything back,
  with the reason, which the console works out from the operation because the
  API's refusal does not carry it:
  - the runtimes are still being released;
  - the entry failed;
  - a node has no snapshot;
  - a node has unresolved interrupted requests.
- **Retry** appears when the hold's entry or restore failed.
- **Reopen without restoring** says what that means: the runtimes are empty,
  and anything still in progress is stopped.
- **The close confirmation** now says that running generations are cut off and
  the runtimes restarted empty, with what each held saved.
- **An operation from an earlier hold** is history and is not shown as
  progress.

The visitors' maintenance page is unchanged on purpose: it shows whether the
platform is closed, the message and the expected return, and nothing about
nodes or models.

- An admin "reset runtime" button. The CLI is the only caller.

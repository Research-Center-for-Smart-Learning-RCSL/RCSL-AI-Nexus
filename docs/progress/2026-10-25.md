# 2026-10-25

## #61, third package: the node agent fences the hold and can stop the runtime

P3 of the plan on #61, stacked on the first package (#77). It adds what the
node and the host need for a forced entry and a verified restore. It does not
yet use them. Entering stays behind `MAINTENANCE_ENABLED`, off by default and
off in production, and the coordinator that drives these pieces is P4.

**On the node agent.**

- **Promotion reads the hold in the database.** An entry takes an advisory lock
  exclusively before it closes the platform. `accepted → running`, the point
  where a send is authorised, takes the same lock shared and reads the hold.
  - Any promotion that commits has therefore read the platform open after every
    entry that committed before it.
  - None can read "open" and commit after the platform closed.
  - A refused attempt becomes `cancelled_unsent` with
    `maintenance_before_send`.
  - The gateway hears 503 `maintenance`, not `overloaded`.
- **A frozen gate.**
  - A promotion that finds the hold closed freezes the gate in the new
    `maintenance` state. So does the watchdog, which reads the hold every tick,
    and so does start-up.
  - A frozen gate stays `maintenance` through reopen, drain and block until the
    hold lifts. It then returns to whatever it would otherwise be: drained,
    blocked or serving.
  - An agent started during maintenance never serves.
- **The final send barrier.** A task promoted just before the freeze is
  withheld at its last in-process step, before the runtime sees a byte, and
  becomes `cancelled_unsent`.
- **Interrupt.**
  - `POST /v1/maintenance/interrupt` cancels every relay still talking to the
    runtime. It acts only for the epoch the database says is closed.
  - Each cancelled attempt becomes `outcome_unknown` with
    `maintenance_interrupted`, which is truthful, and the node stays blocked
    after the hold lifts until a verified reset.
  - The report keeps sender quiescence apart from settlement, so a database
    outage cannot hold up the runtime's stop.
- **A separate control token.**
  - `node_agent_control_token` is a second secret, and only the agent mounts
    it. It must differ from the data token.
  - It is required by drain, resume, block resolution, interrupt, runtime
    control and the resolve CLI.
  - The gateway holds only the data token, which those routes refuse.

**On the host.**

- **The root runtime supervisor.** `scripts/host/runtime_supervisor.py` runs
  as `online.rcsl.runtime-supervisor`.
  - It takes one of three fixed actions on `online.rcsl.ollama`: stop, start
    and restart.
  - It acts through request and receipt files, as the agent already does with
    the witness.
  - A stop unloads the job, so `KeepAlive` cannot respawn it. It then ends the
    daemon and every model runner, signalling a process only after re-reading
    its unchanged PID and start time, and verifies a fresh scan is empty.
  - Each request runs at most once and leaves a receipt.
- **Supervised reset.** `resolve reset` clears an `outcome_unknown` block in
  one command (the reset action #49 §5 handed to this issue).
  - It uses the same ordered witness evidence as `start` and `complete`, with
    the supervisor's restart in between.
  - The receipt is recorded beside the two witness answers.
- **Installation and host acceptance** are in
  [runtime-supervisor.md](../runbooks/runtime-supervisor.md). The supervisor is
  not installed on the Mac yet.

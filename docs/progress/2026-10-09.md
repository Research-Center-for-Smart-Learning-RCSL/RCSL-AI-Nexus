## Node agent（PR4a-1）：只是落地，還沒有接上

設計和六輪對抗審查都在 [#24](https://github.com/Research-Center-for-Smart-Learning-RCSL/RCSL-AI-Nexus/issues/24)
（revision 1–6）。這裡記做了什麼，以及哪些地方刻意還沒做。

**它是什麼。** 每台 runtime 主機一個 process，是那台 runtime 唯一的送出者。gateway 和 admin
之後（PR4a-2）只透過它送生成與 embedding，PR4b 再把其餘所有送出點搬進來。

**這一版沒有任何正式環境效果。** 它不在 `docker-compose.yml` 裡，而在
`docker-compose.node-agent.yml` 這個 override；例行部署不需要它的 secret，也不會啟動它。
gateway 端的接線（PR4a-2）會放在 `NODE_AGENT_ENABLED` 後面，預設關閉；這個旗標要等 PR4b
的「runtime 之外沒有任何送出點」稽核通過、維護者下令後才會打開。

**為什麼要一把主機上的檔案鎖。** Postgres 的 generation 換代，只證明資料庫角色轉移了，
不證明舊 agent 停了：它可能停在「已提交 running、還沒送出」之間。所以選舉是兩把鎖：先拿
named volume 上的 `flock`，再拿節點的 advisory lock。這把 flock 只有 process 死掉才會釋放，
動手寫之前已在這台 Colima VM 上量過（暫停、凍結、SIGSTOP 都不釋放；SIGKILL、stop、restart
會）。鎖檔和它的 inode 綁成一個「lock domain」，第一次被節點認領後就不能換；agent 不 fork
（AST 測試擋 `os.fork`、`subprocess`、`multiprocessing`），因為 fork 出來的子行程會共用同一個
open file description，讓鎖比送出者活得久。

**一個請求怎麼走。** 先看 op id 是否已存在（存在就只回報，不重跑）→ 在 process 內排隊
（拒絕時不留任何資料列）→ 寫入 `accepted` → 等 slot → **在同一把 barrier 裡**檢查 gate 和
主機鎖、提交 `accepted → running`、標記為已放行。block、drain、失去角色都先拿這把 barrier，所以
它們之後不會再放行任何東西，也不存在「已提交 running 但還沒放行」的狀態。之後 relay 一定讀到
runtime 自己的 `done`，呼叫端離開只影響交付。

**什麼算證據。** 完成只認 runtime 的 `done` 或回應，數字用 runtime 的原始 total，不用 chunk
數（Codex 給了 chunk 比 `eval_count` 多的反例）。只有 transport 單次嘗試的 `ConnectError`
算「沒送出」；其他一切（read error、timeout、沒有 `done` 的 EOF、relay 自己的 bug）都是
`outcome_unknown`，整個節點停止派送，包括 embedding。

**怎麼解除封鎖。** 只能走稽核過的兩步驟：先證明送出者已不在、排空自己的工作，對主機 witness
發一個新的 challenge 取得基準 `O1`；操作員重啟 runtime；再發第二個 challenge，同一個 witness
incarnation 回報的 `(pid, start_time)` 必須和 `O1` 不同。witness（`scripts/host/runtime_witness.py`）
先讀 challenge 再觀察，所以帶著某個 nonce 的觀察一定發生在 nonce 之後。它的安裝和實測（含一次
真的重啟 runtime）是維護者已批准、但要另排時段的驗收；在那之前，**任何封鎖都解不開**——這是
接受過的狀態，因為 agent 在那之前不會被啟用。

**順手修的兩件事。** 計數器新增 `measure()`：身分、prompt 計數和宣告的上下文都從同一份
manifest 快照算出（原本 tool call 和 gemma4 的編碼會各自再讀一次）。gateway 的資料庫帳號不能
再讀 `attempt_results`，因為那裡存的是模型輸出，和 `prompt_logs` 同一類。

**刻意沒做的。** 請求綁定、`Idempotency-Key`、用量的 exactly-once 與交付狀態對帳都在 PR4a-2
（schema 已在這一版）；Tier 2、lifecycle、pull、heartbeat 搬進 agent 是 PR4b。

## Node agent（PR4a-2）：gateway 端接上，旗標仍關

PR4a-1 已合併（[#33](https://github.com/Research-Center-for-Smart-Learning-RCSL/RCSL-AI-Nexus/pull/33)）。
這一版把 gateway 和 admin 接到 agent，全部放在 `NODE_AGENT_ENABLED` 後面，**預設關閉，關閉時
行為和之前完全一樣**。

**依節點找 runtime。** 路由選了節點之後，chat、embedding 和 Tier 2 摘要都按那個節點找 runtime，
不再只看 runtime 種類（原本兩個節點時有一半機率送錯主機）。旗標打開時，每個 Ollama 呼叫都走
被選節點的 agent；沒有 `agent_url` 的節點直接拒絕；仍然只按種類查 runtime 的路徑一律失敗，
而不是繞過 agent。還沒轉換的路徑（`/readyz`、residency 掃描、下載、load/unload）留給 PR4b 稽核。

**`Idempotency-Key`。** 旗標打開時，每個 chat 請求在送出前先綁定到唯一一個 attempt：有 key 就綁在
key 上，沒有就綁在一個無法重送的新 id 上。重送同一個 key，在模板、檢索、壓縮之前就回答，
答案來自它綁定的那個 attempt、在它自己的節點上查，**永遠不會再跑一次**：已完成就重播成一個
chunk、不再計用量；還在跑或結果未知、失敗、結果已過期都是 409；同一個 key 換了內容是 422。
agent 根本沒收到的 attempt，要先在 agent 上立墓碑，綁定才能換到新的 attempt。同一個 key 同時
來好幾份，只有一份會跑（測試裡三份是一份跑、兩份 409）。

**用量只寫一次。** 每個 attempt 一列用量，以 attempt 為 key，由同一條純規則從 agent 的終局紀錄
和綁定時的計費快照算出；gateway 在串流結束時結算，tailnet admin 上的 sweeper 補上沒人結算的。
數字來源標明：runtime 的原始 `done` 數字、chunk 數估計、或無法取得（記 0 並標明）。還沒終局
的 attempt 不計費，所以斷線的客戶端不會留下部分用量。`completed` 意義不變（客戶端收到完整回應）：
gateway 只記一次交付結果，沒記錄就維持 false，之後只能由對帳從 false 改成 true。

**還沒做的。** agent 結算的用量還沒送進 Prometheus 指標；用量的讀取和匯出還沒顯示
`totals_source`、`prompt_tokens_basis`；新的錯誤碼等旗標打開時再寫進 gateway 的 API 參考。
「A 掉了回應、重試不能跑到 B」要兩個節點才測得到，單節點測試只證明重送一定回到綁定的節點。

## PR4a 部署與驗收（agent 執行中、閒置，旗標仍關）

- **01:45 部署。** migrate 結束時為 0，所有服務 healthy，port 綁定和健康監測都正常。舊 image 標為
  `rollback-20261009b`。
- **01:48 witness 上線。** root LaunchDaemon `online.rcsl.runtime-witness`，每 2 秒發布一次
  attestation。
- **01:49 agent 啟動**（override，`.env` 加上 `COMPOSE_FILE`）。拿到 generation 1，主機鎖在手上，
  lock domain 綁到節點 `local`；經由 agent 對真的 Ollama 生成一次，終局帶原始 `done` 數字。
- **01:53:52 接管測試。** 在長生成途中 `docker kill` agent；重新啟動後是 generation 3，那筆從
  `running` 變成 `outcome_unknown`（`orphaned_by_takeover`），gate `blocked`，新請求被拒（503）。
- **01:54:47 resolution 基準 O1**：witness 回答新 nonce，看到 pid 41871。沒重啟就嘗試 `complete`，
  被正確拒絕。
- **01:55:18 重啟 Ollama**（`launchctl kickstart -k`），**01:55:27 complete**：O2 是同一個 witness
  incarnation、pid 45933；那筆轉為 `failed`（`resolved_by_reset`），稽核留下 baseline 和 reset，gate
  回到 `serving`，經由 agent 的生成恢復正常。
- **01:55:54–58 模型載回**：gemma4（262144）、qwen（32768）、embedder（2048），`keep_alive: -1`。
  之後經部署好的 gateway 跑一次 `/v1/chat/completions`，回 200，用量照舊路徑寫入。

觀察到的一點：`docker kill` 之後 `unless-stopped` 不會自動重啟 agent，要手動 `up -d`。這記進了
runbook，刻意不改：被殺的 agent 若有進行中的生成，接管後節點會被封鎖，本來就需要人處理。

## 用量的數字來源看得到了

補上 PR4a-2 留下的兩個缺口，旗標仍關，關閉時沒有任何行為改變。

**指標。** agent 結算的那一列，由真正插入它的那個 process 送進 Prometheus：gateway 結算的算在
gateway，sweeper 補的算在 tailnet admin，兩邊加起來每個 attempt 剛好一次（`ON CONFLICT` 輸掉的
那一方 rowcount 是 0，不會再算）。原有的 `nexus_inference_*` 照舊累加，另外多一個
`nexus_usage_settlements_total{capability, model, totals_source}`：`estimated_from_chunks` 和
`unavailable` 的比例就是要盯的數字。之後才由對帳把 `completed` 從 false 改成 true 的，指標不再
重算，以寫入當下為準，那一列才是紀錄。

**讀取。** `/admin/usage/records` 多回 `totals_source`、`prompt_tokens_basis`、`runtime_completed`，
舊路徑寫的列這三欄都是 null。這幾欄原本只在 migration 裡、ORM 沒有，所以讀不出來。用量表上，
不是 runtime 確認的數字會標「output estimated」或「output unknown」，滑過去說明輸入數字的來源。

## Node agent（PR4a-1）：只是落地，還沒有接上

設計和六輪對抗審查都在 [#24](https://github.com/Research-Center-for-Smart-Learning-RCSL/RCSL-AI-Nexus/issues/24)
（revision 1–6）。這裡記做了什麼，以及哪些地方刻意還沒做。

**它是什麼。** 每台 runtime 主機一個 process，是那台 runtime 唯一的送出者。gateway 和 admin
之後（PR4a-2）只透過它送生成與 embedding，PR4b 再把其餘所有送出點搬進來。

**這一版沒有任何正式環境效果。** 它不在 `docker-compose.yml` 裡，而在
`docker-compose.node-agent.yml` 這個 override；例行部署不需要它的 secret，也不會啟動它。
gateway 端的接線（PR4a-2）會放在 `NODE_AGENT_ENABLED` 後面，預設關閉；這個旗標要等 PR4b
的「runtime 之外沒有任何送出點」稽核通過、維護者下令後才會打開。

**為什麼要一把主機上的檔案鎖。** Postgres 的 generation 換代，只證明資料庫角色轉移了，
不證明舊 agent 停了：它可能停在「已提交 running、還沒送出」之間。所以選舉是兩把鎖：先拿
named volume 上的 `flock`，再拿節點的 advisory lock。這把 flock 只有 process 死掉才會釋放，
動手寫之前已在這台 Colima VM 上量過（暫停、凍結、SIGSTOP 都不釋放；SIGKILL、stop、restart
會）。鎖檔和它的 inode 綁成一個「lock domain」，第一次被節點認領後就不能換；agent 不 fork
（AST 測試擋 `os.fork`、`subprocess`、`multiprocessing`），因為 fork 出來的子行程會共用同一個
open file description，讓鎖比送出者活得久。

**一個請求怎麼走。** 先看 op id 是否已存在（存在就只回報，不重跑）→ 在 process 內排隊
（拒絕時不留任何資料列）→ 寫入 `accepted` → 等 slot → **在同一把 barrier 裡**檢查 gate 和
主機鎖、提交 `accepted → running`、標記為已放行。block、drain、失去角色都先拿這把 barrier，所以
它們之後不會再放行任何東西，也不存在「已提交 running 但還沒放行」的狀態。之後 relay 一定讀到
runtime 自己的 `done`，呼叫端離開只影響交付。

**什麼算證據。** 完成只認 runtime 的 `done` 或回應，數字用 runtime 的原始 total，不用 chunk
數（Codex 給了 chunk 比 `eval_count` 多的反例）。只有 transport 單次嘗試的 `ConnectError`
算「沒送出」；其他一切（read error、timeout、沒有 `done` 的 EOF、relay 自己的 bug）都是
`outcome_unknown`，整個節點停止派送，包括 embedding。

**怎麼解除封鎖。** 只能走稽核過的兩步驟：先證明送出者已不在、排空自己的工作，對主機 witness
發一個新的 challenge 取得基準 `O1`；操作員重啟 runtime；再發第二個 challenge，同一個 witness
incarnation 回報的 `(pid, start_time)` 必須和 `O1` 不同。witness（`scripts/host/runtime_witness.py`）
先讀 challenge 再觀察，所以帶著某個 nonce 的觀察一定發生在 nonce 之後。它的安裝和實測（含一次
真的重啟 runtime）是維護者已批准、但要另排時段的驗收；在那之前，**任何封鎖都解不開**——這是
接受過的狀態，因為 agent 在那之前不會被啟用。

**順手修的兩件事。** 計數器新增 `measure()`：身分、prompt 計數和宣告的上下文都從同一份
manifest 快照算出（原本 tool call 和 gemma4 的編碼會各自再讀一次）。gateway 的資料庫帳號不能
再讀 `attempt_results`，因為那裡存的是模型輸出，和 `prompt_logs` 同一類。

**刻意沒做的。** 請求綁定、`Idempotency-Key`、用量的 exactly-once 與交付狀態對帳都在 PR4a-2
（schema 已在這一版）；Tier 2、lifecycle、pull、heartbeat 搬進 agent 是 PR4b。

## Node agent（PR4a-2）：gateway 端接上，旗標仍關

PR4a-1 已合併（[#33](https://github.com/Research-Center-for-Smart-Learning-RCSL/RCSL-AI-Nexus/pull/33)）。
這一版把 gateway 和 admin 接到 agent，全部放在 `NODE_AGENT_ENABLED` 後面，**預設關閉，關閉時
行為和之前完全一樣**。

**依節點找 runtime。** 路由選了節點之後，chat、embedding 和 Tier 2 摘要都按那個節點找 runtime，
不再只看 runtime 種類（原本兩個節點時有一半機率送錯主機）。旗標打開時，每個 Ollama 呼叫都走
被選節點的 agent；沒有 `agent_url` 的節點直接拒絕；仍然只按種類查 runtime 的路徑一律失敗，
而不是繞過 agent。還沒轉換的路徑（`/readyz`、residency 掃描、下載、load/unload）留給 PR4b 稽核。

**`Idempotency-Key`。** 旗標打開時，每個 chat 請求在送出前先綁定到唯一一個 attempt：有 key 就綁在
key 上，沒有就綁在一個無法重送的新 id 上。重送同一個 key，在模板、檢索、壓縮之前就回答，
答案來自它綁定的那個 attempt、在它自己的節點上查，**永遠不會再跑一次**：已完成就重播成一個
chunk、不再計用量；還在跑或結果未知、失敗、結果已過期都是 409；同一個 key 換了內容是 422。
agent 根本沒收到的 attempt，要先在 agent 上立墓碑，綁定才能換到新的 attempt。同一個 key 同時
來好幾份，只有一份會跑（測試裡三份是一份跑、兩份 409）。

**用量只寫一次。** 每個 attempt 一列用量，以 attempt 為 key，由同一條純規則從 agent 的終局紀錄
和綁定時的計費快照算出；gateway 在串流結束時結算，tailnet admin 上的 sweeper 補上沒人結算的。
數字來源標明：runtime 的原始 `done` 數字、chunk 數估計、或無法取得（記 0 並標明）。還沒終局
的 attempt 不計費，所以斷線的客戶端不會留下部分用量。`completed` 意義不變（客戶端收到完整回應）：
gateway 只記一次交付結果，沒記錄就維持 false，之後只能由對帳從 false 改成 true。

**還沒做的。** agent 結算的用量還沒送進 Prometheus 指標；用量的讀取和匯出還沒顯示
`totals_source`、`prompt_tokens_basis`；新的錯誤碼等旗標打開時再寫進 gateway 的 API 參考。
「A 掉了回應、重試不能跑到 B」要兩個節點才測得到，單節點測試只證明重送一定回到綁定的節點。

## #27：qwen2.5 的工具定義，修好了渲染，量不出差別

這個型別沒有 JSON 的 `String()`，所以印成 Go struct。0.33.2 到最新的 0.40.2 都一樣，上游的修正
（ollama/ollama#18391）還沒合併。

**修法：新 tag `qwen2.5:7b-tools`。** `scripts/modelfiles/qwen2.5-7b-tools.Modelfile` 只把那一處改成
`{{ json .Function }}`（`json` 是 Ollama 提供的模板函式），其他從 `FROM qwen2.5:7b` 繼承。runtime 自己

**計數仍然保守。** 驗證語料逐案量 runtime 的 `prompt_eval_count`：新 tag 每個帶工具的案例比舊 tag 多
10 token（欄位名稱），計數器（照 GGUF 的 Jinja 渲染）在每個案例都仍 ≥ runtime，例如 `tools_plain`
237 對 200、`tool_loop_100` 10029 對 9392；不帶工具的案例兩個 tag 完全相同。

**工具呼叫的準確度沒有差別。** `scripts/model-eval/tool_calls.py`：34 個案例，包括相似用途的誘餌工具、

`name`、`description` 的標籤，參數仍是 JSON，函式名稱排在第一個，qwen2.5 看得懂。

## C6b：gemma4 用 runtime 自己的 tokenizer 計數

**C6b 的前提要修正。** 原本的說法是 gemma4 的 GGUF 寫著 `tokenizer.ggml.model = "llama"`，所以 runtime
走 SentencePiece，計數器應該移植 SentencePiece 的相鄰合併。實際讀了 Ollama 0.33.2 的程式碼：它用
llama.cpp b10630 的 llama-server 當 runner，相容層（`handle_gemma4`）在載入前把這個鍵改成 `"gemma4"`，
選到的是 llama.cpp 的 **BPE** 加 `gemma4` 前處理，不是 SentencePiece。runner 回報的 `build_info` 也是
`b10630`。

**所以移植的是那條 BPE。** `gemma4_bpe.py` 和 `native/src/gemma4_bpe.rs` 各一份，照 `llama-vocab.cpp`：
先切出特殊 token（control、user-defined、unknown，加上 llama.cpp 載入時的改寫：結束生成清單上的
文字升為 control，有 `<|tool_response>` 時 `</s>` 降為一般），空白換成 `▁`，依換行分段，整段換行若
本身是 token 就一個 token，其餘按 merge rank 由低到高、同 rank 取最左合併，合不成 token 的按 UTF-8
位元組退回 `<0xXX>`，沒有對應 token 的位元組丟掉（runtime 也丟）。llama.cpp 對等長特殊 token 的排序
不穩定，詞彙裡若有等長且可能重疊的特殊 token 就拒絕精確計數；gemma4 沒有。以前的 HF Unigram 整段
拿掉：只有 gemma4 會走到它，真正的 SentencePiece 詞彙沒有可對照的 runtime，改為按估算計數。

**判準是 runtime 自己的 tokenizer。** gemma4 runner 的 `/tokenize` 回傳 llama.cpp 產生的 token id。
隨機混合（字元、空白、換行、特殊 token 拼法、各種文字、emoji、控制字元）比對：Python 版 3,300 筆、
Rust 版 2,000 筆，**id 逐一相同**。同一批文字上，舊的 Unigram 有 74 筆少算（最多 −6）、102 筆多算，
另外 424 筆根本編不出來。整段 prompt 對驗證語料記錄的 `prompt_eval_count`：U − P 是 0（10 個案例）
或 +2、+3（同時算 thinking 開和關、取大的），以前是 +2 到 +6，沒有負的。

**留在 repo 裡的證據。** `record_tokenizer_goldens.py` 把 runtime 的 id（數量和雜湊）錄成
`gemma4_tokenizer_goldens.py`，共 187 筆，含驗證語料經 `gemma4_renderer` 渲染的整段 prompt；有權重時
兩個後端都要逐一相符。沒有權重時，規則本身由 `test_gemma4_bpe.py` 的小詞彙測試固定。建詞彙 0.33 秒、
峰值記憶體比 Unigram 低（304 MB 對 400 MB）。

**這對 PR2b 的意義。** spec §6 原本說 C6b 之前，gemma4 profile 的驗證只是有限語料上的經驗證據；現在
encoder 是 runtime 自己的演算法並逐 id 對過，剩下會不同的只有渲染（C6c 已逐 byte 對過）和版本變動。

## Node agent（PR4b）：所有送出點都經過 agent，旗標仍關

規格表上 4b 的那一欄做完了：`load`、`unload`、`pull`、`residency` 都由 agent 服務，加上「agent
之外沒有任何 runtime HTTP」的稽核。旗標仍關，關閉時行為只差一個修正（見最後）。

**lifecycle 是獨佔操作。** agent 新增 `/v1/lifecycle/{load,unload,pull}`：先像 drain 一樣關閘，
排隊中的請求在提升前取消、已放行的等到終局，然後在同一把 barrier 下提升（有未知操作時一樣拒絕），
跑完再開閘；操作者自己下的 drain 不會被 lifecycle 結束時打開。load 帶的是登記的 `num_ctx`，和
登記不同就拒絕；模型不在這個節點也拒絕。pull 完成、開閘之前，agent 讀 runtime 對這個 tag 回報的
digest 寫進 `models.manifest_digest`（設計 S5，留稽核紀錄）；讀不到就不改，之後送到新權重的請求會
因 `revision_mismatch` 被拒，是關的不是開的。agent 的資料庫帳號因此多了 `models.manifest_digest`
這一欄的 UPDATE 權限，其他欄位仍不能改。

**lifecycle 結果不確定時是 failed，不封鎖。** 規格只要求推論、摘要、embedding 不確定時封鎖節點；
lifecycle 改變的是 runtime 載了什麼，heartbeat 會再觀察，pull 若可能改了 tag 則由權重 pin 擋下。
接管時孤兒化的 lifecycle 也一樣記為 `failed`（`orphaned_lifecycle`）。migration `d2f6b8a41c93`
把 `pull` 加進操作種類。

**呼叫端都照模型所在的節點找 runtime。** registry 的 load／unload、下載（下載 job 不持有 session，
所以 state committer 多了短交易的 `node()`）、heartbeat 的 residency 掃描、`/readyz`。Tier 2 和
embedding 在 4a-2 已經是了；Tier 2 在綁定之前執行，所以是自己獨立的 unbound attempt，不會和主請求
共用 op id（紀錄的種類仍是 `inference`，不是 `summary`）。

**稽核。** `test_runtime_sender_audit.py` 固定三件事：Ollama 的 `/api/...` 和 MLX 的路徑只出現在
直接 adapter 和 agent 的 relay；這些送出者只在預期的地方被建構；旗標打開時 `build_runtimes` 給每個
依種類的 adapter `NO_RUNTIME_URL`（`.invalid`，永遠解析不到），程序手上沒有任何 runtime 位址，沒有
`agent_url` 的節點拿不到 runtime。網路層沒有動：compose override 只能加網路、不能拿掉，所以
gateway 仍在 `gateway-egress` 上，保證來自程序裡沒有位址，而不是網路不通。

**順手修的：`/readyz` 一直把 runtime 當成健康。** `_probe` 只等檢查跑完就回 True，`health()` 回
False 也算通過。現在 False 就是失敗，健康巡檢會如實看到 runtime 中斷；容器的 healthcheck 用的是
`/healthz`，不受影響。

**打開旗標是維護者的決定**，步驟和兩個要注意的地方（下載會佔住整個節點、封鎖時不能 lifecycle）
寫在 first-deploy runbook。

## PR2b：驗證過的計數 profile 可以用整個視窗

PR2a 的 guard 是 `min(視窗 // 2, 視窗 − 1 − 輸出)`。PR2b 只對「證明計數不低於 runtime」的 profile 拿掉
`// 2`，輸出那一條和全域 `MAX_CONTEXT_LENGTH` 都保留。設計在 #24 經過審查，四點都照做：

- **key 是整組量過的指紋**：節點、runtime 與版本、manifest（完整 SHA-256）、計數程式（encoder 和
  renderer 的原始碼 digest，`gguf_token_counter/fingerprint.py`；native 的由 `build.rs` 在建置時算
  原始碼 digest 寫進擴充模組）、請求形狀（有沒有送工具、`think` 在線上的樣子）。任何一項不同就回到
  舊規則；Ollama 升級、重新 pull、改了 encoder、第二個節點，都不需要人記得去撤銷。
- **版本要新鮮**：heartbeat 經 agent 讀 runtime 版本寫到 `nodes.runtime_version`（migration
  `e9c4b7a52d18`），gateway 只在五分鐘內的觀察下才採用；agent 送出前自己再讀一次 `/api/version`，
  以它為準。provision 每次部署都 merge 節點列，這兩欄刻意不寫，所以部署不會清掉。
- **只有拒絕時才問**：舊規則會放行的請求不查指紋，平常不多付成本。
- **紀錄是 repo 裡的檔案**（`validated_profiles.VALIDATED`），像程式一樣審查。測試在沒有權重時檢查
  紀錄引用的案例存在且形狀相符、Python encoder digest 等於這份程式碼算出的值（改了 encoder 就會
  失敗，提醒重新量）；有權重時逐案確認 manifest、renderer 和 `P ≤ U`。

**第一筆紀錄：qwen2.5:7b，不帶工具。** 它服務 `assist`，也是 `chat` 的備援。帶工具的形狀因為 #27
（Ollama 把工具定義印成 Go struct）不驗證。效果是 qwen 的上限從 16,383 變成 `32,767 − 輸出`。gemma4
不加紀錄：它先被全域 122,880 擋住，加了也不會改變什麼。

**順手讓 qwen 的計數與 runtime 逐 id 一致。** 驗證時用 qwen runner 的 `/tokenize` 對隨機文字比對，
發現約一半不一致：llama.cpp 會把 user-defined token（`<tool_call>`）和它的結束生成清單（`</s>`…）
也當特殊 token 切出來，而我們的 qwen encoder 只切 control 型別，於是把這些字串算成好幾個 token。
方向是多算（2,036 筆中 0 筆少算），但既然要靠它放寬，就改成和 gemma4 port 同一套規則（Python 與
Rust 共用）。改完後 3,036 筆 id 全部一致，錄成 `qwen_tokenizer_goldens.py`（203 筆）；驗證語料上
qwen 不帶工具的案例 U − P = 0。

## Attempt billing after an unsent retry (#32)

Selected the request-binding and exactly-once usage review in the remote
watch list, [#32](https://github.com/Research-Center-for-Smart-Learning-RCSL/RCSL-AI-Nexus/issues/32).
Open PRs #56-#59 cover compaction, grounding, residency, availability,
lifecycle uncertainty and Jev feasibility; none addresses this retry defect.
The review is based on main `cb6f32c` and does not claim to complete the
watch list's other review items.

A binding that never reached its agent can be tombstoned as `cancelled_unsent`
and rebound to a new attempt. The new route and generation were used, but the
original binding's model, start time and compaction snapshot still supplied
usage settlement and the model reference used by replay diagnostics. A real
PostgreSQL/ASGI reproduction showed a
completed retry retaining the old model reference instead of `qwen2.5:7b`.

Each newly inserted attempt now stores its own billing snapshot. The versioned
rebind and snapshot insertion share one transaction, and racing contenders
read the winner. Settlement and replay use the selected attempt's snapshot;
the original request snapshot and each earlier attempt remain immutable.
Gateway grants remain limited to inserting snapshots and updating binding
versions and delivery evidence.

The nullable column allows legacy attempts and older gateway INSERTs to retain
the original binding snapshot as a read fallback. Historical per-attempt facts
cannot be recovered, so existing usage is not rewritten.

**Deployment requires a maintenance window.** Quiesce request traffic and stop
all old `gateway`, `admin-public` and `admin-tailnet` processes, including the
tailnet usage sweeper. Apply the additive migration, then start the corrected
`admin-tailnet` before enabling the corrected gateway and public admin
entrance. Confirm that every old settlement writer has stopped before any new
snapshot writer serves traffic. An old sweeper can settle a new attempt from
the original binding snapshot; the unique usage row then keeps those stale
figures even after a corrected sweeper runs. Schema compatibility alone does
not make that mixed-reader deployment safe.

**Rollback must preserve snapshots.** Quiesce and stop new request writers
first, retaining the corrected settlement reader until every attempt whose
billing differs from the original binding is provably
unsent, or terminal and settled. Accepted, running, missing-agent and unknown
attempts need their normal terminal/cancellation/resolution evidence before
this condition is satisfied; elapsed time does not satisfy it. Reverting that
reader earlier can permanently misattribute an unsettled retry. Keep the
column and attempt history during routine rollback: dropping it destroys
snapshot facts even when usage is settled. A rollback build should retain the
corrected snapshot lookup and settlement paths; the original binary reads
old binding metadata for retained keyed replays. The migration's destructive
downgrade is not the routine operational rollback procedure.

If another pending PR extends the same Alembic head first, rebase this
migration onto that head before merging.

## Attempt billing after an unsent retry (#32)

Selected the request-binding and exactly-once usage review in the remote
watch list, [#32](https://github.com/Research-Center-for-Smart-Learning-RCSL/RCSL-AI-Nexus/issues/32).
Open PRs #56-#59 cover compaction, grounding, residency, availability,
lifecycle uncertainty and Jev feasibility; none addresses this retry defect.
The review is based on main `cb6f32c` and does not claim to complete the
watch list's other review items.

A binding that never reached its agent can be tombstoned as `cancelled_unsent`
and rebound to a new attempt. The new route and generation were used, but the
original binding's model, start time and compaction snapshot still supplied
usage settlement and the model reference used by replay diagnostics. A real
PostgreSQL/ASGI reproduction showed a
completed retry retaining the old model reference instead of `qwen2.5:7b`.

Each newly inserted attempt now stores its own billing snapshot. The versioned
rebind and snapshot insertion share one transaction, and racing contenders
read the winner. Settlement and replay use the selected attempt's snapshot;
the original request snapshot and each earlier attempt remain immutable.
Gateway grants remain limited to inserting snapshots and updating binding
versions and delivery evidence.

The nullable column allows legacy attempts and older gateway INSERTs to retain
the original binding snapshot as a read fallback. Historical per-attempt facts
cannot be recovered, so existing usage is not rewritten.

**Deployment requires a maintenance window.** Quiesce request traffic and stop
all old `gateway`, `admin-public` and `admin-tailnet` processes, including the
tailnet usage sweeper. Apply the additive migration, then start the corrected
`admin-tailnet` before enabling the corrected gateway and public admin
entrance. Confirm that every old settlement writer has stopped before any new
snapshot writer serves traffic. An old sweeper can settle a new attempt from
the original binding snapshot; the unique usage row then keeps those stale
figures even after a corrected sweeper runs. Schema compatibility alone does
not make that mixed-reader deployment safe.

**Rollback must preserve snapshots.** Quiesce and stop new request writers
first, retaining the corrected settlement reader until every attempt whose
billing differs from the original binding is provably
unsent, or terminal and settled. Accepted, running, missing-agent and unknown
attempts need their normal terminal/cancellation/resolution evidence before
this condition is satisfied; elapsed time does not satisfy it. Reverting that
reader earlier can permanently misattribute an unsettled retry. Keep the
column and attempt history during routine rollback: dropping it destroys
snapshot facts even when usage is settled. A rollback build should retain the
corrected snapshot lookup and settlement paths; the original binary reads
old binding metadata for retained keyed replays. The migration's destructive
downgrade is not the routine operational rollback procedure.

If another pending PR extends the same Alembic head first, rebase this
migration onto that head before merging.

PostgreSQL acceptance covers changed routing/time/compaction, one execution
and usage row on replay, three racing rebinds, failed-insert rollback, legacy
INSERT/read/settlement, migration downgrade/upgrade with existing data, and
denied gateway UPDATEs to both snapshot columns. The new retry reproduction
failed before the fix. The full Linux unit suite passed 1,283 tests with 71
skipped cases; all 23 focused PostgreSQL integration cases passed. Strict
Linux mypy passed all 378 application files; full backend Ruff lint and format
checks and 548 documentation links passed. Windows CRLF conversion initially
changed the tokenizer source
fingerprint; exporting with `core.autocrlf=false` reproduced CI's LF content
and resolved that test-environment failure without changing the tokenizer.
No production change or live model inference was performed; the test runtime
is simulated.

## Three independent reviews of PR #57

Three Agents reviewed commit `c0eda7bd` against PR #56's `ad9e48d` base:
routing correctness, security/operations, and test coverage/acceptance claims.
They reviewed without changing code or Git state. The security/operations and

1. The selector required fresh Ollama residency on every node, but the observer
   still queried only the configured local node and cleared remote observations.
   This permanently refused otherwise healthy agent-backed remote models.
2. The availability endpoint reused the authentication transaction. PostgreSQL
   `now()` returned that transaction's start time, while READ COMMITTED could
   see a newer heartbeat commit, incorrectly reporting future/stale evidence.

The local follow-up now observes each node/runtime through its own agent when
agents are enabled. Direct adapters retain their single-host boundary. Tests
use the real runtime directory and agent HTTP adapter with mocked HTTP to
exercise two nodes with the same model ref, a cold primary, a resident remote

During follow-up review, the routing Agent reproduced another timing hazard:
probing all nodes before writing their results could wait minutes for a slow
node and then stamp an older positive result as fresh. The observer now writes
each node/runtime group's result before probing the next group. The regression
test asserts the first group's write has occurred inside the next agent's HTTP
handler, before any wait on that agent can occur.

Availability now reads the database wall clock after loading the model rows and
uses that same captured time for its rolling usage/refusal window. A real
PostgreSQL test opens the reader transaction, commits a later heartbeat through
a second session, and requires the reader to report the fresh model as available.
The selector continues to reject genuinely future timestamps.

## Uncertain lifecycle work stays blocked and enters availability alerts

Remote issues #49 section 6 and #50 identify the next independently shippable
safety gap after PR #56 (compaction and grounding) and PR #57 (availability).
PR4b deliberately treated uncertain load, unload and pull as failed, reopened
the gate, and did the same on agent takeover. A fresh residency snapshot and a
manifest pin cannot prove that an earlier remote operation has finished
changing scheduler state. Repeating a load could race that remote work.

The decision is now to use #24 section 3's uniform node-wide block. Every
uncertain lifecycle outcome is durable `outcome_unknown`, including EOF before
pull success and a response lost after load/unload submission. The dispatcher
blocks before attempting the database write and keeps admitted work tracked
until settlement. Takeover preserves the original sender provenance, fences
late completion and never dispatches its cancelled accepted work. Only ordered
terminal/reset evidence resolves the uncertainty; residency and age do not.

This new PR is based on PR #57 and therefore transitively stacked on #56. It
also carries the already-local `32fb5c8` observation fixes described above,
which were not on #57's remote head when this branch was created. Neither
existing PR branch is changed. #49 and #50 remain open: desired residency,
automatic reload/cancellation, the admin reset action, reconcile/mismatch
metrics and production restart acceptance still require later work. #54 stays
gated on its dependencies and an operator-owned quality evaluation; #27 needs
model/template evaluation; #20 and #32 are research/review tracking rather than
implementation candidates for this change.

Tests cover all three lifecycle kinds, every blocked sender, duplicate attempt
observation, a delayed uncertainty commit, terminal and proven-unsent outcomes,
real PostgreSQL takeover and stale-owner fencing, ordered reset proof, and
availability evidence with no inference traffic. The existing Prometheus rules
and host health delivery consume these newly unresolved operations unchanged.
Validation: the complete Linux unit suite passed **1,396 tests**, with **71
skipped**. **66 focused PostgreSQL 17 integration tests passed** across agent

These use actual migrations and simulated runtime/witness responses. Ruff

reproduced one existing observation timing limit in both base and head. Models

The repository requires an explicit capture time for a non-null observation,
and always clears the timestamp for unknown state. A failed clock read never
falls back to a later write time or a client clock. Test doubles follow the same
contract. This is a freshness repair within #49's observation scope, not an
automatic reload or a change to uncertainty resolution.

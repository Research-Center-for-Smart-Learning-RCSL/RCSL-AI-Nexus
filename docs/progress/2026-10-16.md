## Residency intent and reconciler (#49, offline parts)

Models now carry `desired_resident` and `desired_version`, separate from
lifecycle `state`. The migration starts every row at `desired_resident =
false` and drops cleanly on downgrade. It does not backfill from `state =
'loaded'`: production models were unloaded outside the registry, so those rows
may be stale, and enabling the flag would reload them unasked. The first
operator Load records intent. Operator Load sets intent,
Unload clears it, and `PUT /admin/models/{id}/residency-intent` changes it
without touching the runtime. That endpoint answers `202` and is audited as
`accepted`. It is the cancellation for the post-restart case, where the model is
observed `downloaded` and Unload refuses. The models table shows the intent and
offers **Stop restoring**.

The reconciler runs in the tailnet admin beside the heartbeat. It starts only
when `RESIDENCY_RECONCILER_ENABLED` is set (default `false`), node agents are
enabled and the heartbeat runs, so this deploy changes no behaviour. It:

- acts on two distinct, fresh `downloaded` observations;
- restores largest first through `ManageModels.restore`, with the operator's
  budget and audit and the agent's exclusive lifecycle path;
- re-observes the whole node after each load;
- repairs evicted siblings for at most two rounds, then backs off
  `30 s × 2^n` (cap 15 min);
- gives up on a node, with one error log, after four consecutive failed passes
  that each loaded weights under unchanged intent, so a set that cannot
  co-reside is not reloaded for ever; any intent change on the node resets it;
- re-reads intent before and after each load, and unloads weights whose intent
  was withdrawn mid-load.

It refuses to dispatch while the node has an `outcome_unknown` operation, a
lifecycle operation in flight, a competing reconciler or operator Load (per-node
advisory lock, which an operator Load also takes and refuses on with `409`)
or a suspension. The suspension hook is left for maintenance mode (#61). With
the flag on, the budget applies the final spec's occupancy rule. A fresh
positive absence is not charged.

**Deviation recorded.** The final spec places reconciliation in the node agent.
It runs in the control plane instead, because the memory budget, lifecycle
states and audit live there. Every load still reaches the runtime only through
the agent.

**Deferred.**

- The admin "reset runtime" action (§5). The agent cannot restart the host
  runtime, and the witnessed resolution clears one operation per restart. The
  CLI remains the path.
- Residency-mismatch and reconcile metrics (#50).
- Host acceptance: an operator-owned Ollama restart with no traffic, the
  gemma4, qwen2.5:7b, nomic-embed-text order, an authenticated gateway request
  and the five #23 gates.

Verification: backend unit suite (1,461 passed, 71 skipped), ruff lint and
format, strict mypy (391 files). Frontend `tsc`, ESLint and Vitest (509
passed). New unit cases cover ordering, the two-observation rule, lost and

`error`, the blocked gate before and mid-pass, in-flight operations, a competing

## Colima VM size recorded as 4 GiB

The VM went to 4 GiB on 2026-10-10 by `colima start --memory 4`, but the
LaunchDaemon (`online.rcsl.colima.plist`) and the documents that must change
with it still said 3. The daemon has `KeepAlive`, so a host reboot or the
foreground `colima` process exiting would have restarted the VM at 3 GiB, the
size that OOM-killed production workers during a rebuild. The maintainer kept
4 GiB. The repository plist, the first-deploy runbook and the architecture
documents now say 4; the three-model memory fit was measured at 3 GiB and must
be re-measured at 4 when the models are restored.

The installed copy in `/Library/LaunchDaemons` still carries `--memory 3`.
Installing the updated plist needs sudo and restarts Colima, so it waits for
the next planned restore of the platform.
